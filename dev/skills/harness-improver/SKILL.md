# Harness improver

Use when material feedback exposes a reusable gap, or a related candidate
is surfaced. This is not a second mandatory Agent or a new permission.
The Solve Loop continues independently unless the gap blocks it.

1. Read original evidence and the existing asset. Link a new distinct
   observation with learn observe, not a duplicate candidate. Distinguish
   fact, hypothesis, task-local preference and durable owner policy.
2. In ordinary work, flag or defer nonblocking BDH gaps and continue the
   requested task. If blocked, use an authorized safe fallback or stop the
   affected action. On request, review the inbox and recommend reuse,
   creation, optimization, adjustment, repair or continued deferral.
   Explicit owner scope authorization is required before selection or
   implementation of BDH changes. Prioritize observed impact, recurrence,
   expected benefit and effort; a work reference is not independent proof.
3. Reopen DEFERRED explicitly through review to CANDIDATE. Improve a
   small existing asset; link a separate authorized PR/issue for larger
   unrelated work. Preserve deferral reason and condition.
4. Run targeted regression, Eval and applicable product verification.
   Attach implementation and evidence at the expected revision. Never
   auto-promote, weaken gates or execute untrusted observation text.
5. Persist sanitized history and review through existing L1-L5 rules.
   Link later reuse outcomes and review drift; retire obsolete guidance.

See [dual-loop plan](../../../docs/development/BDH_DUAL_LOOP_DELIVERY_PLAN.md)
and [learning skill](../continuous-learning/SKILL.md).


Prioritize actual product exit conditions over optimizing repeated
activity that should be eliminated. Review task dependency/order,
unnecessary evidence duplication and obsolete live consumers before
automating a costly loop. See [adaptive stages](../../../docs/development/AGENT_WORKFLOW.md#outcome-first-adaptive-stages).
Keep nonblocking improvements deferred; use the existing manual Git
route for unsupported deletion/export instead of expanding BDH by default.

## Owner-invoked improvement cycle (candidate)

An explicit owner request "BDH优化" or equivalent starts one bounded
cycle: review, select, improve, verify, resume product work, reflect.
It authorizes small BDH improvements in the current authorized PR and
resumption of its existing product scope, not a new PR, privilege,
product interface, acceptance waiver, merge or release. Follow L1-L5
review rules. If no active task is established, resolve it from authorized
records; ask only for a necessary missing decision. Do not treat mentions
of the phrase as requests or turn ordinary learning into automatic coding.

1. Resume the last cycle from the [inbox](../../LEARNING_INBOX.md) latest
   cycle entry and linked records. Review previous improvements, actual
   reuse, failed attempts, overhead, open gates and forward candidates.
   Gather recent actual BoxWeave tasks since its evidence boundary across
   relevant sessions: development, debugging, test, CI, delivery and
   recovery. Expand earlier evidence only as needed. Missing coverage
   is unknown, not zero; distinguish samples and estimates.
2. Revisit [development plan](../../../docs/development/BDH_DEVELOPMENT_PLAN.md),
   [R0 research](../../../docs/development/BDH_R0_REUSE_RESEARCH.md),
   [dual-loop plan](../../../docs/development/BDH_DUAL_LOOP_DELIVERY_PLAN.md)
   and relevant follow-up research/deferrals. Use existing learning
   review and opportunity commands as applicable. Recheck original
   deferral reason, trigger, changed prerequisites and current evidence.
   Do not reopen merely because an item is old. Reuse or adapt mature
   mechanisms before inventing new ones.
3. Choose one small improvement or tightly related group using recurrence,
   expected benefit, cost, risk and testability. Define a baseline,
   comparison scope and unchanged acceptance oracle first. Record why
   alternatives remain deferred or rejected. If no valuable change is
   justified, record no-new-asset and continue the product task.
4. Implement and verify under the existing improver and verification
   rules. Prefer deterministic scripts for repeated execution, observation
   and records; keep Agent judgment, design and creative work explicit.
   Preserve original operations and checkpoints. No self-promotion.
5. Resume the original product task and actually use the improvement.
   Compare nested calls (including failed attempts, waits and pages),
   manual orchestration, rework, elapsed time when available, continuity
   and delivery outcome. Include improvement/setup overhead and shifted
   costs; claim benefits only at equivalent measured scope.
   Continue independent ready work during CI; preserve unmet gates.
6. Append a concise cycle entry to the existing learning inbox; link
   canonical candidate revisions, work/evidence records and previous
   cycle rather than duplicate their contents. Include evidence window
   and current product PR/head, prior improvement review, historical
   research/deferral dispositions, chosen objective and validation,
   actual reuse results and limitations, and ranked forward candidates
   with reconsideration triggers. End with next safe product action,
   pending originals and explicit stop reason if incomplete. The next
   cycle begins from this entry and reflects on its actual outcome.

This is a discoverable procedural candidate, not an automatic external
trigger, scheduler, proven efficiency gain or replacement for immutable
learning histories. Use the Finish Gate before handoff. One request
authorizes one bounded improvement cycle; it does not recursively launch
further BDH maintenance.
