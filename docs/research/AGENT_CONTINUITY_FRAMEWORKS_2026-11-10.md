# Agent workflow engines: durable progress, attribution, search and safe recovery

**Research recorded 2026-11-10 UTC.** Cross-framework lessons for the **BoxWeave native-operation boundary only**. This is not a request to embed Temporal, LangGraph, CrewAI, an orchestration service, a scheduler, memory, a message broker or their workflow semantics in v1.

## Framework-by-framework, two dimensions

| System (current official evidence) | Current capability / design pattern | Failure cases and valuable lesson for BoxWeave; excluded parts |
|---|---|---|
| **Temporal** [Workflow Execution](https://docs.temporal.io/workflow-execution), [Visibility](https://docs.temporal.io/visibility), [Go Continue-As-New](https://docs.temporal.io/develop/go/workflows/continue-as-new) | Distinguishes stable **Workflow ID**, execution **Run ID**, durable Event History, Queries/Signals/Updates, indexed Search Attributes for *operational discovery*, and immutable execution evidence. Replays history after crashes. | A stable work label and separate Agent execution instance make sense; **read the original durable event, don't reproduce an effect based on model intuition**. Search/visibility is for discovery, not authority, consistency of command execution or synchronization. Do not introduce replay code interpreter, activities engine, signals or distributed scheduler. |
| **LangGraph** [checkpoint implementation](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/README.md), [functional replay](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx), [durable execution](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph) | `thread_id` + checkpoint ID, state snapshots, pending writes for completed nodes in failed supersteps, and resumption of recorded results instead of blindly executing successful nodes again; idempotent external side effects must be separated. | A checkpoint of **Agent decisions/Git state** can complement BoxWeave's **actual native effects**. Checkpoint text isn't proof that a Box was created: independently query exact Operation and Incus UUID. Do not store graph/node/thread execution or model messages inside BoxWeave. |
| **CrewAI Flows** [official persisted Flow state](https://github.com/crewAIInc/crewAI/blob/main/docs/v1.14.7/en/concepts/flows.mdx) | `@persist` retains flow state, `state.id` allows restore; may fork from an older state into a new run. Uses SQLite by default in documented example. | Keep a separate stable work reference and per-Agent attempt reference. **Branching a workflow must not silently fork ownership of an already-dispatched Box mutation or its idempotency key**. Do not add Crew/role assignment or a second Flow store to BoxWeave. |
| **Temporal AI agent example** [memory, state, exactly-once illusion](https://docs.temporal.io/ai/featured/memory-state-stripe) | Records activity outcomes and uses stable external idempotency keys for real side effects. Event History does **not** automatically inject an Agent's thought process into a model UI. | Explicitly separate observed native result, Agent checkpoint and presentation/client delivery. An unavailable client cannot self-resume by storing more data on the server. |

## Four user-requested capabilities — what to borrow and not borrow

**1. Persisted operation / crash recovery.** Temporal makes durable history central; LangGraph restores completed node results. BoxWeave already has a narrow SQLite `operations` + `operation_events` journal, worker admission and original UNKNOWN lock. Preserve and enrich that **single** source: immutable original intent, exact authenticated actor, idempotency key digest, first target UUID/incarnation, original native operation ID, typed transition and independent postcondition. Never implement *general workflow replay*: native Exec/create/delete cannot be assumed reversible or exactly-once from transport responses.

**2. Agent/work IDs.** Temporal's Workflow ID/Run ID and CrewAI's state.id are useful vocabulary, but their semantics differ. For v1 use: **trusted `actor_id`/token ID** from actual auth; optional **untrusted `agent_ref`** for self-declared caller execution; optional **untrusted `work_ref`** to group actions across different actors. Names don't confer permissions or global uniqueness. The same `work_ref` may exist on separate BoxWeave layers and must not imply any cross-layer access.

**3. Query by Agent/work.** Temporal Visibility is indexed, but searches are not a substitute for a strongly consistent single-operation read. Implement indexed bounded **`operation_list` filtering after authorization** for `work_ref`, `agent_ref`, authenticated actor and state/time, with opaque pagination and a stable ordering; `operation_get` remains the exact current truth. Results can be delayed or incomplete under retention, and must expose coverage rather than imply work is finished. Self-reported filter values cannot pierce another actor/Project boundary.

**4. Structured result and safe next read.** Workflows return a stable handle; BoxWeave should return original `operation_id`, `tracking_id`, current state and evidence, version/layer, safe `next_action`: `operation_get(original_id)`, `operation_output_get` if authorized, or `host_local_review` for original UNKNOWN. **No next_action that blindly retries a mutation, creates a replacement Box or cancels original effects.** One response must not contain entire guest command/output logs.

## Critical limits and product edge

- **A task checkpoint is a consumer-owned document**, not the native operation journal. It records objective, accepted design, repo SHA/dirty status, action/evidence links, original Operation IDs, next safe steps and reasons. A suddenly crashed Agent may lose its newest unpersisted reasoning; resume must reconcile Git/Box/CI before acting. The checkpoint may live in Git or any trusted workflow store; BoxWeave needs no new Task Checkpoint MCP endpoint.
- **Identity vs authority:** changing tokens or having multiple Agent clients connected never means they share an actor; a client-provided `agent_ref` is audit correlation only. The current v1 TokenInfo.UserID maps to token ID and is currently **not a stable human/Agent user registry**. Add no RBAC/Agent registry under this proposal. Shared-work search returns only records the authenticated role may already see.
- **Concurrent Agents:** both may mutate distinct owned Boxes if native ownership/locks permit. Same Box conflicting writes must serialize/refuse via existing resource/intent lock semantics. A common `work_ref` is not a distributed lock or order guarantee. Audit each **authenticated actor + attempted request + original operation** separately.
- **Retention and privacy:** a checklist shouldn't retain guest stdout or tokens; store references and digests. The SQLite audit journal's retention is not extended simply because a human task checkpoint exists. Historical `UNKNOWN` evidence stays protected until separately authorized safe reconciliation. No claims of full-text searchable log retention.
- **Stop scope creep:** no generic Agent tasks/list, flow steps, scheduler, delegated token minting, shared hidden thoughts, messaging, automatic worker reassignment, Agent heartbeat, or cross-host orchestration. Those are workflow platform responsibilities.

**Recommended product boundary:** *BoxWeave reliably executes and proves owned Box operations; an Agent/workflow client decides what the broader job means and how to hand it over*. The two can integrate via optional correlation and a small checkpoint document.
