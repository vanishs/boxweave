# Containarium nested Incus and AppArmor: evidence for BoxWeave v1

Research date: 2026-11-13 PT. Source: [FootprintAI/Containarium](https://github.com/FootprintAI/Containarium), public \`main\` at \`55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606\` when inspected. Read current source files, the project's explicit native results and selected relevant commit diffs; **not** a line-by-line audit, executed native test, reproduction of its claimed successful cloud environment, or proof that upstream head and any published binary are identical.

This is a **narrow addendum** to the existing [Containarium implementation/history audit](CONTAINARIUM_MAIN_HISTORY_2026-11-07.md), which already covered general SDK, lifecycle, egress, file and operation incidents. It focuses on the specific 2026-11-13 BoxWeave v1 RC physical-host failure documented separately in [real v1rc MCP/AppArmor evidence on Draft PR #136](https://github.com/vanishs/boxweave/blob/fix/v1-apparmor-nested-host-preflight-20261113/docs/verification/V1_RC_PHYSICAL_HOST_NESTED_APPARMOR_2026-11-13.md).

## Executive finding

**Containarium contains positive evidence that a nested Incus can start and create an LXC, but no retrieved result proves that an unprivileged LXC which is itself an enforced Incus-managed instance can successfully initialize yet another full Incus and launch a third-level LXC with AppArmor profile administration intact.** Its success cases must not be transferred to the BoxWeave L0 -> L1 (Incus 7.6) -> L2 (Incus 7.6) -> L3 requirement without checking privilege and namespace details.

Three materially different topologies occur in the same repository:

| Upstream scenario | What its actual report supports | Difference from v1rc's failed L2 |
| --- | --- | --- |
| Cloud-box nested Incus / system-container cluster nodes | Design says a nested Incus on a Containarium cloud box **launched and ran Ubuntu 24.04 LXC**. Amendment reports k3s running inside an unprivileged node and fixes containerd sysctl behavior without granting \`security.privileged\`. | Shows a nested daemon creating **its first child**, not proof that the child can initialize another Incus daemon and create a **grandchild**. Original cloud-box AppArmor profile/namespace, versions and kernel were not pinned in that design paragraph. |
| \`nested-incus-pod\` benchmark (#1565) | The actual 2026-08-26 report confirms \`incus admin init\`, managed bridge/dnsmasq, an unconstrained child \`incus launch\` and successful \`incus exec\` **inside a Kubernetes pod**. | The pod explicitly uses **\`privileged: true\`**, plain runc, and Incus default child profile. It is not a nonprivileged, enforced-AppArmor L2. It also failed to create any **resource-limited** Containarium boxes because cgroup delegation failed. |
| Incus VMs as separate backends | An Incus **VM** hosts its own kernel and nested Incus for LXC tenant boxes; design/provisioning recorded with CPU/GPU nuances. | A VM creates a **kernel security boundary**; not the shared-kernel nonprivileged LXC -> LXC -> LXC chain that v1 is evaluating. |

## Dimension 1 — current implementation, not just README claims

1. **Native Incus SDK config.** \`pkg/core/incus/client.go\` constructs the instance and writes \`security.nesting=true\` when \`EnableNesting\` is requested. Separately, \`EnablePodmanPrivileged\` writes **\`security.privileged=true\` and \`raw.lxc\` with \`lxc.apparmor.profile=unconfined\`**. Those flags are not implicit in all LXC creates and must not be described as the universal Containarium default. [Pinned code](https://github.com/FootprintAI/Containarium/blob/55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606/pkg/core/incus/client.go).
2. **Privilege is a product/security decision, not an AppArmor namespace delegation fix.** \`internal/server/privileged_policy.go\` gates the privileged-Podman route with \`all\`, \`admin-only\`, or \`disabled\`; the currently **unset** setting defaults to \`all\` for backward compatibility. A configured unrecognized policy fails closed. It is a known high-risk privilege widening, acknowledged in [security claims](https://github.com/FootprintAI/Containarium/blob/55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606/docs/security/CLAIMS.md) and [source](https://github.com/FootprintAI/Containarium/blob/55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606/internal/server/privileged_policy.go). A set-but-blank value is rejected in the inspected \`parsePrivilegedPolicy\` source, even though some historical commit text describes blank as default-all; current source takes precedence.
3. **The container-node probe does not certify nested AppArmor policy administration.** \`ContainerNodeCapable\` checks LXC driver, cgroup v2, \`br_netfilter\` and overlay module presence. Its \`probeNesting\` calls an available \`lxc\` driver *transitive evidence* that nesting was allowed. It does **not** load an AppArmor policy in an already-enforced child or prove a second-generation nested \`incus_dnsmasq\`. Good for its intended k3s-node feasibility, not a validation of BoxWeave L3. [Current probe](https://github.com/FootprintAI/Containarium/blob/55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606/pkg/core/cluster/containerprofile.go).
4. **CI host workarounds are not production requirements.** \`scripts/ci-incus-container-host.sh\` disables \`kernel.apparmor_restrict_unprivileged_userns\` on its disposable runner and sets iptables FORWARD ACCEPT. This is an explicit **host-global test-environment relaxation**, not an AppArmor policy-namespace delegation proof or a safe recommendation for the owner's fresh physical host. [Pinned script](https://github.com/FootprintAI/Containarium/blob/55b244c0e7a65cecf8bd8f6dd4b19a74dbdec606/scripts/ci-incus-container-host.sh).
5. **Upstream's own safety claims are qualified.** \`docs/security/CLAIMS.md\` calls unprivileged LXC scoped, notes the privileged-Podman exception, and marks per-container AppArmor-profile claims **not verified in that review**. Do not convert a feature flag or GitHub Actions pass into actual native policy evidence.
6. **Incus version discussions are about a different failure.** The Containarium README/deployment notes recommend Incus 6.19+ to avoid an older Ubuntu Incus 6.0 AppArmor/Docker-in-LXC defect (CVE-2025-52881). This is **not** evidence that the physical L0 7.5.1 -> L1/L2 7.6 mix caused v1rc's L2 \`apparmor_parser\` policy-admin denial; matching exact versions and native policy readback are still necessary.

## Comparison with the actual v1rc L2 failure

Owner-confirmed **L0 Incus 7.5.1 server/client**, unprivileged/nesting L1 with Incus 7.6 and internal \`unconfined\` at AppArmor namespace level 1; installed v1 RC creates an **enforced-profile** restricted L2 in **the same level-1 namespace**. L2's Incus 7.6 starts, but its first \`incus admin init\` fails while loading \`incus_dnsmasq-incusbr0\`: \`apparmor_parser\` exit 243, \`Access denied. You need policy admin privileges to manage profiles.\` L3 was not attempted.

**No matching positive/negative control in the reviewed Containarium sources reproduces that exact AppArmor profile inheritance and security model.** The Containarium Kubernetes pod, VM and cloud-box examples are different topologies. The observed v1rc failure therefore remains **UNRESOLVED**, and the L0 7.5.1 versus nested 7.6 version-compatibility hypothesis remains **UNTESTED**, not proven or excluded.

For a newly reinstalled physical host, a useful bounded experiment is to record actual L0 server version/kernel/AppArmor, then compare L1 and L2 \`/proc/1/attr/current\`, \`.ns_name\`, \`.ns_level\`, \`.ns_stacked\`, effective Incus profile and **real single-dispatch native initialization**. Prefer a matched Incus version control before attributing causes to version skew; separately prove internal dnsmasq, L3 Create/Exec, cgroup ceilings, and packet isolation. **Do not** copy the disposable-runner AppArmor sysctl relaxation, set \`security.privileged=true\`, set \`raw.lxc\` unconfined, remove AppArmor, or alter L0 security policy merely to produce a green \`incus launch\`.

## Disposition

- This is research and experiment design **only**. No native/installed Containarium binary was run by this review; no BoxWeave product code or host config change is proposed here.
- Preserve the existing v1 product boundary (single native official Incus Go SDK path, 20 public MCP tools, nonroot restricted Project, original Operation/UNKNOWN). PR #136's static hard-refusal heuristic remains separately unapproved for merge; the owner has raised a valid objection to hard-failing based only on heuristics.
- Whether safe AppArmor policy-namespace delegation beyond L2 is possible on the specific kernel/Incus pair remains an upstream technical question. No safe general-purpose full-L3 configuration was established by these Containarium materials.
