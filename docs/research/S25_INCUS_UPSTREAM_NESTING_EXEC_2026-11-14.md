## BH-018: exact Incus 7.6 Exec dispatch/guest-start boundary

[Incus v7.6.0 `instance_exec.go`](https://github.com/lxc/incus/blob/v7.6.0/cmd/incusd/instance_exec.go) creates a background `OperationClassTask/CommandExec` and returns `OperationResponse(op)`. The asynchronous `run` function later prepares optional `record-output` files and calls `inst.Exec(post, nil, stdout, stderr)`. If that invocation returns an error, `run` immediately returns the error **before** reaching `cmd.PID()`, `cmd.Wait()` or `metadata["return"] = exitStatus`. The latter return metadata is populated only **after** an `inst.Exec` successfully returns a process object and `cmd.Wait()` runs. The REST endpoint separately rejects `record-output` + `wait-for-websocket`, matching BoxWeave's current supported mode.

**Precise implication:** A nonempty original native Incus Operation ID establishes **API/operation dispatch**, not necessarily that an executable started in the Guest. An error from the async `inst.Exec` can produce a terminal failed native Operation **without** `metadata.return`. The current BoxWeave `ExecEvidenceFromFinal` demands `api.Success` plus `return`, and therefore conservatively keeps such events UNKNOWN. Do **not** reinterpret the original missing-`gpg` operation merely from its executable name, a vanished native Operation, or a generic terminal native failure. To improve classification, first prove via exact pinned SDK/Incus, operation status/error, typed startup-failure witness, stdout/stderr path behavior and absence of a Guest PID that **this particular command never started**. Preserve the original BoxWeave/native IDs even in any later verified terminal failure.

**Next focused source+native experiment (not yet executed):** In a wholly separate disposable native harness, run the *official SDK* `ExecInstance` using the same `RecordOutput=true,WaitForWS=false` and inspect the original native Operation record for (a) nonexistent binary, (b) executable permission denied, (c) existing binary exit 1, (d) Guest execution with missing/invalid cwd, (e) SDK timeout/lost ACK. Separate `FAILURE before Guest PID` from `SUCCESS + metadata.return=1`, and distinguish missing evidence from proof of no Guest effects. Require regression fixtures for native Operation error details and `UNKNOWN` on ambiguity. No automatic retry.

## BH-019: AppArmor, BPF, ID maps are separate security boundaries

1. [Incus v7.6.0 `driver_lxc.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc.go) explicitly chooses `localUtil.AppArmorProfile()` **when the inner daemon is already AppArmor-confined or lacks AppArmorAdmin**. Only the other code path builds a new instance profile, and only when stacking is supported but the *daemon itself* is not already stacked does it add the per-instance namespace. When Incus AppArmor integration is disabled entirely, the driver instead requests `lxc.apparmor.profile=unconfined`. This strongly predicts both earlier observations: L1 host and disposable B shared AppArmor namespace; the diagnostic Incus AppArmor disable caused the nested LXC process to try changing its label to `unconfined` and be refused. **Disabling Incus AppArmor is not a safe fix.**
2. [Official system-call interception documentation](https://linuxcontainers.org/incus/docs/main/syscall-interception/) says paired `security.syscalls.intercept.bpf=true` and `security.syscalls.intercept.bpf.devices=true` enable a narrowly identified devices-cgroup BPF interception feature. Incus uses host-side mediation for eligible unprivileged calls and describes material risk if exposed to untrusted workloads. [Instance keys](https://linuxcontainers.org/incus/docs/main/reference/instance_options/) default both to false; prior exact expanded L1-parent config proved **these keys were absent**. A controlled, individually flagged disposable-parent A/B comparison is warranted, but **not** automatic exposure to all Agent-owned Boxes.
3. [BPF token delegation](https://linuxcontainers.org/incus/docs/main/explanation/bpf-tokens/) is a newer *different* upstream mechanism (kernel >=6.9; exact delegated `security.bpffs.*` map/program/attach/command allowlists). It is **not equivalent** to BPF syscall interception, nor evidence that this LXC cgroup-device failure can be fixed by arbitrary token settings. [Incus release note](https://linuxcontainers.org/incus/news/2025_10_31_21_13.html) states project low-level rights are needed for delegation, creating another restricted-Project security gate. Examine as a later narrowly authorized alternative, never `any` by default.
4. [Maintainer's Incus-inside-Incus discussion](https://discuss.linuxcontainers.org/t/incus-container-inside-incus/23146) explains the user namespace constraint: nested unprivileged-in-unprivileged may not have spare usable UIDs/GIDs; an inner `security.privileged=true` instance may still be *host-unprivileged*, but loses isolation **relative to its direct parent**. Do **not** use this as a product default or confuse outer-host safety with inter-Agent/parent security. The [official project restriction](https://linuxcontainers.org/incus/docs/main/reference/projects/) explicitly defaults `restricted.containers.privilege=unprivileged`, and separately gates nesting, BPF interception and low-level configuration. This is a control to retain for BoxWeave.
5. [March 2026 Ubuntu Noble AppArmor nesting thread](https://discuss.linuxcontainers.org/t/apparmor-breaking-nested-incus-on-ubuntu-noble/26353) contains real differential evidence: nesting enabled **before** guest launch (or restart after change), Ubuntu→Ubuntu success in one VM topology, Ubuntu host→Debian guest `dnsmasq` runtime EACCES in another. That is **not the same error** as our `apparmor_parser` policy-admin exit 243, but justifies a distro/stacking matrix only after the exact policy error is separately controlled.
6. [Incus network security](https://linuxcontainers.org/incus/docs/main/explanation/security/) notes that parent NIC IP/MAC anti-spoof settings can block inner container bridge/`macvlan` traffic using different L2 identity. A successful nested container start is **not** a network/ACL security PASS; need routed/NAT egress, anti-spoof, and real positive/negative probes.
7. [Incus Project/user-socket security](https://linuxcontainers.org/incus/docs/main/explanation/projects/) confirms `incus` group uses a restricted per-user project; `incus-admin` grants broad daemon/host access. Earlier experiments changing the `incus-user.service` environment alone had no effect on the main `incus.service`. Do not conflate user-socket authentication with root daemon process configuration.
