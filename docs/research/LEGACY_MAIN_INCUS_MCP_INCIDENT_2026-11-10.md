# Legacy main host/MCP incident — evidence and v1 design lessons

**Incident:** 2026-11-09 PT / 2026-11-10 UTC. **Evidence:** owner-operated legacy `dev` host and connected ChatGPT MCP, original CLI/performance/packet outputs, [cleanup issue #123](https://github.com/vanishs/boxweave/issues/123) and [main-only PR #124](https://github.com/vanishs/boxweave/pull/124). **Status:** retrospective research, not installed `v1` acceptance or a decision to expand the product. Read only for matching S2/S5 questions; [permanent product boundaries](../decisions/PRODUCT_BOUNDARY.md) override implementation ideas.

## Observed sequence, with causal uncertainty

1. **Many running instances and severe I/O contention.** The legacy Box inventory had **47 RUNNING managed Boxes**; native `containarium list` reported **49 RUNNING Incus instances**, including two internal core services. On the same host, `/proc/pressure/io` reported some avg10 about **99.37** and full avg10 about **43.14**, with CPU iowait around **67–68%** at one diagnostic point. Incus and bcachefs work threads were observed blocked in I/O; the pool used the Incus `dir` storage driver over an SSD/HDD bcachefs tier, with OS root sharing the HDD. No isolated per-guest IOPS attribution or measured explanation established which element caused the slowdown. **Listed Box quotas were configured capacity, not actual utilization; do not equate bcachefs device Use% with a full filesystem.**
2. **Incus database availability symptom.** One local request failed with `failed to create cowsql connection: no available cowsql leader server found`. Subsequent native inventory succeeded. This establishes temporary database **unavailability**, **not Cowsql corruption**, a proven Incus regression, or a particular cause. Earlier separate nested Incus 7.6 Cowsql leader-loss events are tracked under [O-025](../verification/OPEN_RISKS.md); do not conflate the environments.
3. **Conservative cleanup, improved user experience.** The owner explicitly approved 31 exact-name legacy disposable Boxes for deletion, avoiding core services, the three development fixtures and original UNKNOWN resources. A fresh authenticated BoxWeave MCP read later returned **16 RUNNING managed Boxes** with `unreachableBackends=[]`, retaining `boxweave-test-cli`, `boxweave-test-ser` and `boxweave-test-ser2`. The owner reported much better responsiveness. **Temporal association is not a controlled causal experiment:** “49 running Boxes killed Incus/Cowsql” remains a hypothesis, not a proven finding. Native core services were outside the logical MCP count.
4. **MCP integration failed after apparently successful OAuth.** The owner restored an operator-managed Cloudflare Quick Tunnel and configured the public origin. Legacy `boxweave http doctor` showed loopback discovery, but ChatGPT accepted an OAuth password/consent screen then showed “cannot update app / retry” during Tool refresh. Independently issued test-token `tools/list` calls succeeded over **both local `http://127.0.0.1:18844/mcp` and public HTTPS `/mcp`: HTTP 200, 70 tools, no JSON-RPC error**. Those reads proved *those probes*, not the actual ChatGPT connector's URL, authorization or complete lifecycle. Legacy 70 tools are **not** v1's approved 20.
5. **Actual HTTP path clue.** Header-only operator capture on port 18844 during client refresh showed repeated **`POST /` → HTTP 405**, **`POST /token` → 200**, **`GET /.well-known/openid-configuration` → 404**, plus other HTTP 200 replies. The legacy JSON-RPC MCP endpoint is **`POST /mcp`**, *not* `POST /`. An optional OIDC discovery 404 is not sufficient evidence of a broken MCP/OAuth setup. After focusing on the full connector endpoint ending in `/mcp`, the owner reported recovery and the connected ChatGPT BoxWeave MCP **actually returned the 16-Box inventory**. The originally saved connector URL and any internal redirects were **not independently captured**: wrong-root routing is the strongest observation, not a universal proof of the precise misconfiguration.
6. **Protocol-version problem was separate.** Legacy `main` accepted an initialize request with HTTP header **and** JSON-RPC body version `2025-11-25` (HTTP 200), but returned 400 when both were changed to `2025-06-18`. That experiment changed two inputs, so could not isolate the rejecting branch. [main PR #124](https://github.com/vanishs/boxweave/pull/124) introduced version negotiation and [v0.50.5](https://github.com/vanishs/boxweave/releases/tag/v0.50.5) was published/installed. **ChatGPT Tool refresh still failed after that installation, before the root-path investigation.** The compatibility issue is worth remembering but must **not** be presented as the established root cause of this incident.
7. **Agent workflow appeared stalled.** The owner observed the Agent unable to advance when MCP calls failed or seemed hung; earlier read/diagnostic calls returned internal errors. There was no end-to-end trace proving any *specific* native Incus operation ran forever. A blocked client can be waiting for HTTP, server code, an upstream daemon, database I/O or the frontend Tool orchestration, all of which have different recovery semantics.

## Lessons to carry into the official-SDK v1, without historical baggage

- **Diagnose layers independently:** host disk/CPU/IO pressure; Incus daemon/Cowsql health; BoxWeave SQLite and durable worker; MCP loopback `initialize`/`tools/list`; external Tunnel proxy route; client-supplied URL/auth; the *original* native operation and owned UUID. A healthy systemd process, a successful OAuth form or reachable local HTTP socket is **not** an authenticated end-to-end Tool success. A transient Incus `NotFound` or timeout is never proof that a possibly-dispatched write did not occur.
- **Use established upstream ownership:** v1 uses the **official Incus Go SDK and official MCP Go SDK**, not `main`'s parallel MCP/REST paths, bespoke JSON-RPC parser or provider-specific error conversions. Prefer typed native errors, bounded contexts, resource-specific limits, actual native readback and one immutable Tracking/operation journal. A saturated host can look like an application defect; don't add layers of arbitrary timeout translations or automatic “repair” until the failing boundary is known.
- **No Incus/Cowsql database repair subsystem.** Even if heavy guest load contributed to loss of a Cowsql leader, the BoxWeave boundary is to provide honest degraded/unavailable/UNKNOWN outcomes and preserve identity/reconciliation. No automatic Cowsql DB repair, bcachefs reconfiguration, Incus restart, filesystem repair, forced deletion, foreign instance adoption or a new host-monitoring daemon is approved. Host-local authorized operators may choose exact safe cleanup or official recovery; not a remote MCP action.
- **Watch actual load, not Box count.** `dir` storage and tiered SSD/HDD may involve I/O amplification/background work, but that was not proven. Build modest stress scenarios and conservative concurrency/backpressure with actual disk latency/PSI and exact Instance/Project identifiers; do not treat CPU/memory/disk *limits* as consumption or assume “idle RUNNING” is inherently hot. Stop on ambiguous destructive cleanup.
- **Endpoint includes path.** A public origin `https://host` is *not* the MCP service URL `https://host/mcp`. For a user-operated Cloudflare Tunnel or proxy verify the intended Host, exact path, Method, SDK initialize/negotiated version, authenticated `tools/list` from the **actual client**, and a harmless read-only Tool. Capture an intentionally bad `POST /` → 405 case as a useful operator troubleshooting signal. A generic OAuth success or GET metadata alone is insufficient. **V1 does not add OAuth/OIDC or Web management**: those are legacy-main observations only.
- **Negotiate protocol with the SDK.** Legacy main had a hardcoded MCP version and [a patch](https://github.com/vanishs/boxweave/pull/124); v1 should use the *official* MCP Go SDK behavior, validate legacy/current initialize/discover, header vs body negotiation, omitted optional JSON-RPC `params`, typed malformed-version rejection, and the current auth/Origin/Host boundaries. Do not copy the old bespoke version allowlist. The regression is valuable **even though it was not the demonstrated connector fix**.
- **Silent journal is not zero traffic.** The legacy user systemd journal showed no request error during the failure, while loopback packets proved there was HTTP traffic. Permit bounded, **operator-local** method/path/status observations (excluding query/capability paths) when debugging; don't log or expose access tokens, Cookies, OAuth codes, request bodies or packet payload. Do not create a public host-log MCP Tool.

## Open S2/S5 design discussion — can an Agent distinguish “working” from “dead”?

The owner's practical concern is valid: a single stalled MCP call can stop the Agent's visible work. Yet **an HTTP heartbeat only proves an HTTP listener is answering**, not that Incus, a guest command or an original durable write is progressing. Equally, the Agent/client may not be capable of issuing a separate probe while its Tool invocation is blocked; server-side timers cannot guarantee ChatGPT will resume its reasoning.

**Candidate approach, not an approved subsystem:** first use the existing `host_status`, immutable original `tracking_id`/`operation_id`/native-operation ID, a sanitized phase/last-observed-progress indicator, finite `operation_get(wait_ms)` (currently maximum 20 seconds), bounded read-only retries and explicit client/server/worker native deadlines. Return an honest transport-unavailable/operation-UNKNOWN distinction. If the client can issue a separate read concurrently, test that as a liveness probe; otherwise document the limitation. Never replay a possibly dispatched create/delete/Exec just because a heartbeat failed. A new daemon, extra public MCP Tool, infinite background polling or distributed lease service needs a separate owner product decision.

| Phase | Scenario to consider | Evidence needed |
|---|---|---|
| **S2** | Existing durable Box create/Exec admitted, HTTP reply lost, worker restarts or Incus read is delayed/DB-unavailable | Original native ID and UUID, no duplicate dispatch, bounded state query, truthful terminal/UNKNOWN evidence |
| **S2** | Distinguish quiet legitimate long-running Exec from blocked MCP/native read; optional independent status polling | Exact wait timeout, last observed progress vs actual native operation; never infer success or abort from missing heartbeat |
| **S2/S5** | Controlled slow I/O and moderate concurrent Box operations on disposable host | Backpressure, resource locks, typed degraded response, no native database repair or foreign cleanup |
| **S5** | Operator-configured external `/mcp`, negative `POST /`, client protocol negotiation, authenticated `tools/list` + harmless read | Observed full client flow; no false PASS from just OAuth/metadata/TCP |
| **S5** | Agent tool call stalls or client disconnects after native dispatch | Client behavior limitation recorded; journal survives, original outcome reconciled without replay |
