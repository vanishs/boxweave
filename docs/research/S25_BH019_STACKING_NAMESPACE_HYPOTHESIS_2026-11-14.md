# S2.5 BH-019 — AppArmor Policy Namespace + Stacking: upstream source review and falsifiable hypothesis (2026-11-14)

> **Status: RESEARCH ONLY / BH-019 BLOCKED.** This note evaluates a user-supplied hypothesis, **not** a verified workaround or an acceptance of recursive Incus. It must not trigger host policy relaxation, privileged containers, admin-socket access, historical UNKNOWN recovery, or mutation of preexisting L0/L1 Boxes. SELinux excluded by owner scope.

## Question and three independent acceptance levels

Target is a recursively nested sequence of **independent, unprivileged** Incus daemons (Host → A → B → C → …) where every daemon owns a distinct policy namespace, can *safely* manage its child AppArmor policies, and all ancestors retain enforced restrictions.

- **Level 1 (guest lifecycle):** a next-level container starts and can exec. Alone, this does not prove policy separation or authority.
- **Level 2 (policy administration):** the inner daemon can create/use its own AppArmor policy namespace and load, replace, remove profiles **within that namespace**, with enforced denials and without editing an ancestor/sibling namespace.
- **Level 3 (recursive):** both Level 1 and Level 2 hold at two successive userns depths under independent sibling/tenant negative controls. A single successful generation is not a general proof.

## Grounded facts (exact sources vs field observations)

1. **Maintainer suggestion, not deep-nesting proof.** Stéphane Graber, November 16 2024, proposed a namespaced *unconfined* stacked label instead of plain `unconfined` for a separate networking/sysfs restriction: [original forum](https://discuss.linuxcontainers.org/t/unable-to-update-some-network-settings-when-apparmor-is-enabled/22109/3). His explanation is that the container remains in an AppArmor namespace so it can still interact with/load policy. The conversation did **not** verify a second/third independent policy namespace, actual inner policy-admin capability, or secure recursive Incus. **Do not use this label as a product default.**
2. **Policy stacking restricts by intersection.** [AppArmor aa-exec manual, STACKING](https://apparmor.net/man/master/aa-exec/) says every stacked profile is evaluated and allowed privileges intersect. `//&` marks a stack; `:namespace:profile` refers to policy in a namespace. An inner `unconfined` component cannot overturn an ancestor explicit deny. Conversely replacing a genuinely enforced outer profile with local `unconfined` may *remove* a defense layer and must not be misrepresented as equivalent isolation.
3. **Pinned Incus v7.6.0 behavior.** [`driver_lxc.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc.go) around lines 1072–1103 checks `AppArmorConfined || !AppArmorAdmin` and in that branch uses the inherited current profile. Otherwise, it appends `profile//&:instanceNamespace:` only if `AppArmorStacking && !AppArmorStacked`. [`apparmor.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/apparmor/apparmor.go) around lines 82–95 explicitly *skips* `createNamespace` when `AppArmorStacked` is true. [`instance.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/apparmor/instance.go) supplies profile-template `feature_stacking` only when `AppArmorStacking && !AppArmorStacked`. These are intentional guard branches, not proof that changing them is safe.
4. **LXC mirrors this condition.** [`src/lxc/lsm/apparmor.c` on main](https://github.com/lxc/lxc/blob/main/src/lxc/lsm/apparmor.c) (observed blob `256f8c12cbf691dcb5856b3d017e2d1873d9691d`) uses `aa_can_stack && !aa_is_stacked` for generated stack transitions and namespace creation; its code checks `/sys/kernel/security/apparmor/.ns_stacked`. A raw LXC label can be specified, but manual label construction cannot itself prove namespace creation or grant policy-admin rights. **Source-version caveat:** `main` is not guaranteed identical to the liblxc build installed with Incus 7.6; pair behavior with exact installed LXC version in later tests.
5. **Actual Linux kernel permission predicate.** [upstream `security/apparmor/policy.c`](https://github.com/torvalds/linux/blob/master/security/apparmor/policy.c), observed blob `63f7821b4dfff04667d5510354cf4a3a954d3c07`, `aa_policy_view_capable` needs visible namespace, appropriately privileged identity, and for non-init UserNS `unprivileged_userns_apparmor_policy != 0 && user_ns->level == view_ns->level`. `aa_policy_admin_capable` also demands `CAP_MAC_ADMIN` and unlocked policy. Consequently **CAP_MAC_ADMIN alone, .ns_stacked=yes alone, and a writable securityfs mount alone are not sufficient**.
6. **Independent upstream observation.** [Canonical LXD issue #14770](https://github.com/canonical/lxd/issues/14770) quotes AppArmor maintainer John Johansen (Jan 2025): *stacking itself has no such depth cap*, but AppArmor then only properly distinguished root UserNS and first child; [Mar 2026 follow-up](https://github.com/canonical/lxd/issues/14770#issuecomment-4044762627) still tracks an underlying Linux issue and deliberate skipping of restacking. This issue concerns LXD/snapd, not direct Incus certification, but matches the independently pinned Incus and kernel checks. [Mar–Apr 2026 Incus Ubuntu Noble vs Debian Trixie thread](https://discuss.linuxcontainers.org/t/apparmor-breaking-nested-incus-on-ubuntu-noble/26353) additionally demonstrates OS-image, dnsmasq/socket and idmap differences; treat them as separate failure classes, **not evidence that the proposed namespaced-unconfined label fixes all nested levels**.
7. **Already measured BH-019 native result.** [Prior project audit](S25_APPARMOR_MULTILEVEL_LSM_LIMITATION_2026-11-14.md) on Linux `7.0.0-43-generic`, Incus 7.6, actual Box C: the L1 parent and both L2 children reported the **same** AppArmor namespace name; children had enforced individual profile names and separate userns, but actual L2 `apparmor_parser` load failed policy-admin **exit 243**. [Pinned root causes](S25_BH018_019_PINNED_ROOT_CAUSES_AND_HOST_GATE_2026-11-14.md) reproduce the failure on separate one-use Azure kernel and compare BPF device interception on/off. Starting the child and reporting enforce does *not* show per-generation policy-admin ownership.
8. **Other independent blockers remain.** The native nested failures include `BPF_PROG_LOAD EPERM` and `newuidmap uid_map EPERM` on some one-use/container setups. These are **distinct** cgroup-device BPF and UID/GID mapping gates; no AppArmor label experiment alone can be declared sufficient. Rootless cgroup, memory/storage, bridge/IPv6 and isolation must be evaluated independently.
9. **Recent kernel patches are not an authorization repair.** [CVE-2026-23405 fix](https://git.kernel.org/stable/c/306039414932c80f8420695a24d4fe10c84ccfb2) caps AppArmor namespace nesting to prevent resource exhaustion; the limit (e.g., 32) does **not** mean 32 safe independent Incus levels. [July 2026 resource-quotas patch proposal](https://www.mail-archive.com/apparmor@lists.ubuntu.com/msg13008.html) describes namespace policy budgets as a *series*, not proof of merge into the actual running kernel or a solution to `aa_policy_view_capable`. No verified kernel baseline enabling safe deeper delegation is identified in these sources.

## Single highest-value next hypothesis and safe experiment

**H1 (diagnostic only):** On a **separate, disposable native VM** with a pinned Incus 7.6, known kernel, exact LXC and parser builds, a parent-managed namespaced-unconfined **test label** might allow a first inner daemon to administer profiles inside its *correctly matched* AppArmor policy namespace while an independently enforced ancestor policy remains active. However, stock Incus `AppArmorStacked` guards are expected to prevent **automatic** per-child namespace creation at the following depth. The hypothesis is **not** that the override establishes recursion by itself.

**A/B approach, without providing/applying a host override:**

- **A (default positive/negative control):** disposable unprivileged `security.nesting` instance under a *known enforced* ancestor. Record per-generation kernel/userns depth, AppArmor policy NS identity/depth, `.ns_stacked`, current effective label, precise Incus/LXC versions, and scoped native receipts. Require actual policy load/reload/deny on L1, then L2.
- **B (isolated diagnostic):** test the upstream-mentioned label form **only in one-use VM fixtures**, comparing one variable and preserving a separately enforced ancestor/sibling boundary. Confirm whether the *actual* inner daemon has policy-admin at each generation, not merely that service boot succeeds. If B disables outer enforced mediation or weakens cross-tenant deny, **FAIL immediately** regardless of launch success.
- Require the L1 and L2 userns/policy-ns levels to match the kernel authorization condition; their AppArmor namespace identities must be **distinct per owned generation**. Independently demonstrate child load/reload/unload of a unique harmless scoped profile, positive behavior under policy, expected enforced denial, denial of sibling/ancestor policy changes, and no escape from parent policy. Then repeat at L3 only if L2 passes and within explicit resource/depth bounds.
- Independently test cgroup-device BPF load/**attach and enforcement** and UID/GID mappings; a PASS of AA policy admin does not close those gates. Record all native original IDs, audit reason, and clean only exact test-owned instances.
- A result of `L2 RUNNING`, `.ns_stacked=yes`, `policy parser -Q success`, or `label unconfined` **without actual policy-admin, per-depth namespaces and denial checks is NOT PASS**. A missing kernel capability or AppArmor `not policy admin` gives BLOCKED, not reason to relax host enforcement.

**Decision after H1:** If B improves first-level admin but stock Incus still inherits the namespace at the next UserNS depth, **stop trying label variants**; move to a **minimal upstream-reviewable Incus/LXC + kernel policy-namespace delegation proposal**, including explicit subordinate namespace ownership, level-aligned view and bounded quotas. Do not blindly delete `!AppArmorStacked` guards: it may expose invalid transitions, policy-namespace DoS or cross-tenant privilege. If no safe supported implementation is possible, record container-depth limitations and evaluate a *true VM kernel boundary* as a separately approved alternative topology.
