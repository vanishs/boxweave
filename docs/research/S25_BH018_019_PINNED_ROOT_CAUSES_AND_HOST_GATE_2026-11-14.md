## BH-018: two independent upstream causes, both verified

**1. Real Guest exit 126 or 127 is mislabelled by a pinned Incus source rule.** Incus tag `v7.6.0`, [`internal/server/instance/drivers/driver_lxc_cmd.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc_cmd.go), blob `c71e0158caf9d32de2bff99ece62a2d30d646113`: `lxcCmd.Wait()` reads the attached command exit status, then *unconditionally* maps **127** to `ErrExecCommandNotFound` and **126** to `ErrExecCommandNotExecutable`. [`cmd/incusd/instance_exec.go`](https://github.com/lxc/incus/blob/v7.6.0/cmd/incusd/instance_exec.go), blob `0567fd8dbc530347e9d751c28d3708a30b308ecf`, stores `metadata["return"] = exitStatus` **after** `cmd.Wait()`, then propagates its error as the final native Operation `Failure` (400). This means `Failure + metadata.return=126/127 + the associated error string` **does not distinguish Guest process-start failure from an executed program's voluntary exit**.

Earlier real native 7.6 control in disposable C showed the same `Failure / Command not found / return=127` for missing binary and an existing shell that wrote `EFFECT_OCCURRED` before exit 127. **New independent 126 test on disposable D**: existing `/bin/sh` wrote `EFFECT_126` to `/tmp/s25-bh018-126-marker` inside `s25-bpf-ab-default`, then exited 126. Original *inner* native Operation **`09a95df8-b2bc-48af-ac2f-c1e28208b89a`**: `Failure`, `status_code=400`, `err="Command not executable"`, `metadata.return=126`, stdout/stderr paths present. The same controlled wrapper independently read back `EFFECT_126`. Parent original BW **`b1fa5bc7bb57b3365f1d1a842884ce48`**, outer Incus **`b31d632a-2206-4ecd-877b-83cd3780df17`**, SUCCEEDED, Guest shell exit 0. Thus **both 126 and 127 are proven ambiguous**. Do not classify either as an absence of Guest effects or auto-retry/unlock original unknown.

**2. Native async Operation terminal evidence is extremely ephemeral (5 seconds).** Exact Incus tag `v7.6.0`, [`internal/server/operations/operations.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/operations/operations.go), blob **`46ff03d3f76344e19d74d73f63ac935ba5ec502d`**, explicitly schedules a goroutine with **`time.After(time.Second * 5)`** after completion, then deletes the original operation from the internal map and native DB. In disposable D, a **new** controlled raw Exec `/bin/true` returned original inner native Operation **`951b7080-0f57-4066-920d-46f5d99b6d6e`**, `Success / metadata.return=0` on immediate `GET /wait`; after 7 seconds, `GET /operations/951b...` returned **`Operation not found`** while the native `/instances/s25-bpf-ab-default/logs/exec-output` listing retained the exact corresponding `exec_951b...stdout` and `.stderr` filenames. Outer BW **`2b863a16ef27e6d7dced7d1c3bef9cb5`**, native **`291addd9-568d-4681-a43c-a6505f0ed2da`**, SUCCEEDED with wrapper exit0. This explains why a later exact native Get can fail even when the operation **certainly ran and finished**. Recorded-output retention is a *separate* lifetime; filenames alone cannot recreate trustworthy signed/typed terminal status.

**BoxWeave design gate:** Current `internal/native/box.go` invokes official `ExecInstance(... RecordOutput:true, WaitForWS:false)`, durable-ACKs the original native ID, then `ObserveUntilFinal` polls `GetOperation` every 400 ms; `ExecEvidenceFromFinal` accepts **only** `api.Success`, a numeric `metadata.return` and bounded authorized output paths. This is conservative and avoids falsely treating a native error as pre-dispatch failure. Failure modes: native terminates as 126/127, short original terminal lifetime, lost ACK, worker crash/restart or delayed verification. **Do not retroactively clear historical UNKNOWN using error text or missing native operation.**

**Proposed engineering work, not yet accepted:** introduce *separate* distinctions for `native operation dispatched`, `native final observed/terminal exit value`, `requested command itself definitely began`, `guest exit success`, `effects may have occurred`, and `replay authorized`. Consider a typed `NATIVE_TERMINAL_FAILURE_WITH_GUEST_EXIT` receipt when the **original** final Operation has valid matching ID, recognized exact terminal error and a valid numeric `return` with originally recorded output paths—this denotes a **known terminal exit**, *never* proof the executable did or did not start. Persist exact raw final/status/error/paths in SQLite before they disappear. Only after product threat-model review could such a receipt be finalized without the generic UNKNOWN lock; no automatic replay. Keep UNKNOWN on missing/ambiguous original final, failed journal commit, lost ACK or untrusted paths. Independent I+N+V required.

**Source regression:** `internal/native/bh018_127_native_outcome_test.go` now includes both 126 and 127 side-effect ambiguity. It guards current safety behavior, not a completed product enhancement.

## BH-019: pinned Incus and AppArmor source explain the false-positive privilege check

**D live read-only layer comparison** from BW `127567af65f159d79ead80d590e47c2c` above:
- Parent D `/proc/self/attr/current=unconfined`, AppArmor `.ns_name=incus-user-1001_s25-bh019-bpf-ab-d-1114_<var-lib-incus>`, `.ns_stacked=yes`.
- Its nested A and B children `s25-bpf-ab-default`, `s25-bpf-ab-enabled` each had enforced distinct per-child `incus-*_<var/lib/incus>` labels yet **the same exact `.ns_name` as their parent**, `.ns_stacked=yes`. Their effective caps `CapEff: 000001ffffffffff` **include bit 33 `CAP_MAC_ADMIN`** (and bit32 `CAP_MAC_OVERRIDE`). This does **not** imply they can actually load kernel AppArmor policy. Both A/B were already independently shown RUNNING with and without BPF interception, respectively; these are *shallow controls*, not new L3 PASS.

**Incus v7.6.0 code paths:**
1. [`internal/server/sys/apparmor.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/sys/apparmor.go), blob **`7394db0704b78934f570e070a8c5268177a337aa`**, sets `AppArmorAdmin=true` if `haveMacAdmin()` (effective `CAP_MAC_ADMIN`) and either outside a user namespace or already `.ns_stacked=yes`; **it does not test actual kernel policy-load permission or deny because the current process is AppArmor-confined**. Separately sets `AppArmorConfined=true` when the daemon's `/proc/self/attr/current` is nonempty/non-unconfined; logs that per-container profiles are disabled.
2. [`internal/server/apparmor/apparmor.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/apparmor/apparmor.go), blob **`99c67421c64fcd67449980dfb4077fc796991962`**: `loadProfile` skips only when `!AppArmorAdmin`, not when `AppArmorConfined`; `createNamespace` deliberately skips when `AppArmorStacked`. Consequently a confined nested daemon may **think it has policy-admin ability because its effective caps and stacked flag look sufficient, then receive 243 at actual profile load**. This is a source-backed **compatibility/feature-detection hypothesis**, not a confirmed upstream issue diagnosis.
3. [`internal/server/instance/drivers/driver_lxc.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc.go), blob **`ee3e8be0df424f38d3e2a55f6ba364be419f0c50`**, chooses current **inherited** AppArmor label if `AppArmorConfined || !AppArmorAdmin`. It generates a new `profile//&:new-namespace:` only if stacking is available and **not already stacked**. [`internal/server/apparmor/instance.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/apparmor/instance.go), blob **`b4d6100719b22d4294369d56959ce902e5686995`**, likewise uses `feature_stacking=AppArmorStacking && !AppArmorStacked`. Thus even an improved kernel alone **does not guarantee** unlimited policy namespaces under the present Incus per-layer implementation.

**Independent upstream concurrence:** [Canonical LXD issue #14770](https://github.com/canonical/lxd/issues/14770) remains **open** and labelled **Blocked Waiting on an external task** as of the current read. An AppArmor maintainer's 2025 note distinguishes stacking depth from kernel User Namespace identification depth. The **Jan 9, 2026** LXD 6.6 retest still reproduced failed `apparmor.service`; the **Mar 3, 2026** traces show actual `.replace` open/write `EACCES` even when `security.nesting=true`; **Mar 12, 2026** maintainer comment links known upstream Launchpad **LP#1652101** and documents intentional `feature_stacking=false` when already stacked. The upstream reproducer's other BPF cgroup-device EPERM is also separately similar to ours. This is compelling corroboration, **not** proof the exact L0 Ubuntu kernel has the same internal implementation fault.

A [Jul 22, 2026 AppArmor policy namespace quota patch series](https://www.mail-archive.com/apparmor@lists.ubuntu.com/msg13008.html) notes that delegated namespaces, when possible, can create uncapped profile/namespace/kernel-memory demand and proposes budgets. It is **NOT** proof that the underlying nested-user-namespace compatibility defect has been fixed or that the patch is in this running Ubuntu kernel. Any future delegation must have resource/namespace caps and be reviewed for inter-Agent isolation.

**Working conclusion:** Prior exact C chain: nested=true+restart failed `dnsmasq` profile 243; no-NIC image unpack failed `archive` profile 243; empty child init succeeded but start failed `incus_<instance>` profile 243. Prior L1 RC4 B original 7.6 and 7.0.2 showed the same deny; disabling daemon AppArmor caused **different** LXC label-transition and BPF EPERMs. This is **not** solved by a broad BPF intercept, `security.nesting=true`, APT upgrade, root vs restricted user socket, lack of ID ranges or any measured flag alone.

**Next safe decisive test:** in a dedicated, administratively approved *physical host* or upstream-compatible kernel/Incus build with real writable AppArmor policy-ns capability, establish **each nesting level's separate delegated policy namespace and usable policy-admin** using the same original native markers, then create/start a second deeper native container *with independent enforced profile*, and separately probe BPF cgroup devices and network/ACL negative cases. Compare kernel+Incus version/source commits and whether `AppArmorAdmin` is a false positive vs actual delegation. **Do not** use `security.privileged=true`, `raw.lxc=...unconfined`, global AppArmor disable, broad BPF token delegation or admin daemon socket on the restricted public agent endpoint as a product bypass. Distinguish any diagnostic workaround that merely inherits the parent policy from true per-layer isolation; the former cannot sign BH-019 secure N-level PASS.

**Boundary:** The accessible L0 RC3 MCP grants Box-scoped Guest execution, **not physical-host root or kernel policy namespace administration**. Do not falsely claim the kernel/Incus fix is installed. Current evidence supports **BH-018 PARTIAL, BH-019 BLOCKED, Draft PR**, plus a concrete upstream report template.
