## BH-018: two independent upstream causes, both verified

**1. Real Guest exit 126 or 127 is mislabelled by a pinned Incus source rule.** Incus tag `v7.6.0`, [`internal/server/instance/drivers/driver_lxc_cmd.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc_cmd.go), blob `c71e0158caf9d32de2bff99ece62a2d30d646113`: `lxcCmd.Wait()` reads the attached command exit status, then *unconditionally* maps **127** to `ErrExecCommandNotFound` and **126** to `ErrExecCommandNotExecutable`. [`cmd/incusd/instance_exec.go`](https://github.com/lxc/incus/blob/v7.6.0/cmd/incusd/instance_exec.go), blob `0567fd8dbc530347e9d751c28d3708a30b308ecf`, stores `metadata["return"] = exitStatus` **after** `cmd.Wait()`, then propagates its error as the final native Operation `Failure` (400). This means `Failure + metadata.return=126/127 + the associated error string` **does not distinguish Guest process-start failure from an executed program's voluntary exit**.

Earlier real native 7.6 control in disposable C showed the same `Failure / Command not found / return=127` for missing binary and an existing shell that wrote `EFFECT_OCCURRED` before exit 127. **New independent 126 test on disposable D**: existing `/bin/sh` wrote `EFFECT_126` to `/tmp/s25-bh018-126-marker` inside `s25-bpf-ab-default`, then exited 126. Original *inner* native Operation **`09a95df8-b2bc-48af-ac2f-c1e28208b89a`**: `Failure`, `status_code=400`, `err="Command not executable"`, `metadata.return=126`, stdout/stderr paths present. The same controlled wrapper independently read back `EFFECT_126`. Parent original BW **`b1fa5bc7bb57b3365f1d1a842884ce48`**, outer Incus **`b31d632a-2206-4ecd-877b-83cd3780df17`**, SUCCEEDED, Guest shell exit 0. Thus **both 126 and 127 are proven ambiguous**. Do not classify either as an absence of Guest effects or auto-retry/unlock original unknown.

**2. Native async Operation terminal evidence is extremely ephemeral (5 seconds).** Exact Incus tag `v7.6.0`, [`internal/server/operations/operations.go`](https://github.com/lxc/incus/blob/v7.6.0/internal/server/operations/operations.go), blob **`46ff03d3f76344e19d74d73f63ac935ba5ec502d`**, explicitly schedules a goroutine with **`time.After(time.Second * 5)`** after completion, then deletes the original operation from the internal map and native DB. In disposable D, a **new** controlled raw Exec `/bin/true` returned original inner native Operation **`951b7080-0f57-4066-920d-46f5d99b6d6e`**, `Success / metadata.return=0` on immediate `GET /wait`; after 7 seconds, `GET /operations/951b...` returned **`Operation not found`** while the native `/instances/s25-bpf-ab-default/logs/exec-output` listing retained the exact corresponding `exec_951b...stdout` and `.stderr` filenames. Outer BW **`2b863a16ef27e6d7dced7d1c3bef9cb5`**, native **`291addd9-568d-4681-a43c-a6505f0ed2da`**, SUCCEEDED with wrapper exit0. This explains why a later exact native Get can fail even when the operation **certainly ran and finished**. Recorded-output retention is a *separate* lifetime; filenames alone cannot recreate trustworthy signed/typed terminal status.

**BoxWeave design gate:** Current `internal/native/box.go` invokes official `ExecInstance(... RecordOutput:true, WaitForWS:false)`, durable-ACKs the original native ID, then `ObserveUntilFinal` polls `GetOperation` every 400 ms; `ExecEvidenceFromFinal` accepts **only** `api.Success`, a numeric `metadata.return` and bounded authorized output paths. This is conservative and avoids falsely treating a native error as pre-dispatch failure. Failure modes: native terminates as 126/127, short original terminal lifetime, lost ACK, worker crash/restart or delayed verification. **Do not retroactively clear historical UNKNOWN using error text or missing native operation.**

**Proposed engineering work, not yet accepted:** introduce *separate* distinctions for `native operation dispatched`, `native final observed/terminal exit value`, `requested command itself definitely began`, `guest exit success`, `effects may have occurred`, and `replay authorized`. Consider a typed `NATIVE_TERMINAL_FAILURE_WITH_GUEST_EXIT` receipt when the **original** final Operation has valid matching ID, recognized exact terminal error and a valid numeric `return` with originally recorded output paths—this denotes a **known terminal exit**, *never* proof the executable did or did not start. Only after product threat-model review could such a receipt be finalized without the generic UNKNOWN lock; no automatic replay. Keep UNKNOWN on missing/ambiguous original final, failed journal commit, lost ACK or untrusted paths. Independent I+N+V required.
