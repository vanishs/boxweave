**Verdict: BH-019 BLOCKED; direct L2 secure native lifecycle unproved.** This report is research and narrowly scoped read-only native verification, not an AppArmor workaround, privileged configuration or acceptance of BoxWeave nested deployment. ## High-confidence upstream explanation (not Incus-only configuration bug)

1. [Canonical LXD #14770, *Apparmor doesn't work in nested containers*](https://github.com/canonical/lxd/issues/14770) is a directly analogous nested-LXC/AppArmor reproduction. In a January 13, 2025 comment, AppArmor maintainer John Johansen notes that *profile stacking itself is not subject to a depth cap*, but AppArmor's user namespace handling can properly distinguish **only root namespace and first child**. Do not confuse these distinct claims. The issue remained **open** / **Blocked Waiting on an external task** at observation time; comments dated 2026-01-09 and 2026-03-03 explicitly reproduced AppArmor policy-load **exit 243** despite `security.nesting=true`. A 2026-03-12 maintainer comment refers to upstream Linux/Ubuntu kernel issue [LP#1652101](https://bugs.launchpad.net/ubuntu/+source/linux/+bug/1652101) and explains why a container manager avoids repeated profile stacking. LP status was **not independently fetched**, so do not infer a current upstream kernel fix or version threshold from this reference.
2. [Incus v7.6.0 LXC driver code](https://github.com/lxc/incus/blob/v7.6.0/internal/server/instance/drivers/driver_lxc.go) chooses the inherited AppArmor profile when the *inner Incus daemon* is already confined or lacks AppArmor-admin capabilities; it adds a per-instance profile namespace only if stacking is supported and the **daemon is not already stacked**. [Incus v7.6 AppArmor namespace implementation](https://sources.debian.org/src/incus/7.6.0-1~exp1/internal/server/apparmor/apparmor.go) independently skips namespace creation when `AppArmorStacked` is already true. These controls strongly predict inheritance of an existing namespace by generation 2 and policy reload denials. A local policy bypass flag does **not** make deeper safe namespace ownership appear.
3. [AppArmor 4.1 policy-loader source](https://sources.debian.org/src/apparmor/4.1.0-1/parser/rc.apparmor.functions) describes nested containers whose AppArmor namespace was not independently created: their startup may experience profile-load failures and the loader explicitly calls this an **unsupported** configuration. This supports the native *policy-admin* diagnosis; it is not proof of an exact future Incus release solution.
4. [Incus project restrictions](https://linuxcontainers.org/incus/docs/main/reference/projects/) explicitly gate nesting, privilege, low-level profile configuration and system call interception. Giving child Incus unrestricted raw LXC or host Incus-admin is NOT a least-privilege proof. [Incus security policy](https://linuxcontainers.org/incus/docs/main/explanation/security/) rejects routine privileged/untrusted admin-socket access.

## Meaning for safe BoxWeave architecture and next tests

- **Do not continue guessing alternative Incus 7.6 service environment variables** or applying global AppArmor-disabling flags. The current blocker is stronger than `security.nesting` and distinct from BPF-device interception. It is consistent with a Linux AppArmor LSM/userns ceiling as documented by upstream; the precise path to a safe delegation in this kernel is not yet verified.
- **Next test = positive-control depth boundary on a disposable native host:** read AppArmor namespace and security posture for an Incus-managed first child (already PASS) and second child (policy-load FAIL), then vary *only* a kernel/AppArmor build known by upstream to address multi-level delegation **if such a version exists**. Require per-generation distinct writable namespaces and negative access/policy-admin proof; mere `.ns_stacked=yes` is insufficient. No supported upgraded kernel baseline is yet identified.
- **Alternative topology evaluation:** a new KVM-capable native L0 guest or VM boundary can provide a fresh kernel security namespace for deeper levels **if** KVM and the isolation/readback can be genuinely verified. Prior L1 host `/dev/kvm` check was negative. A theoretical VM fallback is not presently an accepted remedy.
- **If no upstream-supported secure deep nesting exists:** document N-level unprivileged *container* recursion as a platform limitation, and differentiate actual required isolation levels from conceptual BoxWeave controller hierarchy. Any architectural simplification must be explicitly approved, not silently substituted for the owner's requested nested functionality.
- **Keep BH-018 independent:** the earlier native Exec case `Failure/Command not found/return127` collides with a side-effecting shell returning 127; do not reinterpret those original UNKNOWN effects as pre-dispatch.
