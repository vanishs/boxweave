# 阶段 7 提示词｜全局优化、降低新技术债、固化长期知识维护

你是系统审查和长期维护 Agent。项目已完成主要实现与集中验证。本阶段要确保它不仅“能运行”，还**容易被人和下一位 Agent 理解、验证、调整和继续开发**。

## 进入检查

- 确认位于新 Worktree/分支，旧工作区只读。
- 阅读 `AGENTS.md`、`docs/INDEX.md`、`docs/product/`、`docs/design/`、`docs/process/IMPLEMENTATION_PLAN.md`、`docs/verification/`、`docs/knowledge/`、`PHASE_STATUS.md` 和 `HANDOFF.md`。
- 检查阶段 6 是否已完成关键验收；未通过的高优先级事项必须先显式列为阻碍或退回相应阶段。
- 重新检查旧分支最新 SHA 与 `LEGACY_SYNC.md`，将仍然有效的知识更新纳入评估，不合并旧代码。

## 核心任务

1. 以当前代码和真实测试为依据审查：模块边界、重复逻辑、过度抽象、复杂数据流、难以测试的部分、性能热点和操作成本。
2. 只做能证明有价值的简化与优化；每项变动说明预期收益、风险与对应回归测试。
3. 清理阶段 4/5 积累的临时代码、无用配置、过时代码路径；不得因“清理”删除仍有价值的证据、回归测试或历史决策记录。
4. 全面审查知识库：去重、修正过时结论、标记被替代的 ADR、排除错误信息、修复文档链接、统一术语和 ID。
5. 保证 `AGENTS.md` 保持短小，明确新 Agent 的开工必读、代码变更时的文档更新义务、测试命令、禁止修改旧分支的边界、旧知识增量审阅方法。
6. 形成可执行的日常维护流程：接收新需求 → 查来源 → 修改 `REQ/AC` → 更新 ADR/任务 → 编码与测试 → 更新知识索引和验证矩阵 → 提交交接。
7. 指定各类信息的唯一权威文件，避免将同一结论散落在多处造成分歧。
8. 进行“冷启动交接测试”：假设换一个完全没参与重建的 Agent，仅依赖 `AGENTS.md` 和 `docs/INDEX.md`，能否找到产品目标、实现边界、运行命令、设计依据、测试和剩余风险？记录发现并修正。

## 完成判断

- 任一核心功能可以从 `REQ/AC` 追到实现、测试和证据。
- 重要设计能够解释为什么这样做、何时需要重新审视。
- 实际执行启动/测试命令，结果与文档一致；未执行的检查有明确说明。
- 旧项目继续迭代时，新项目有明确定期或按阶段的**知识审阅机制**，不需要合并旧提交。
- 新 Agent 可以在无私人聊天上下文的情况下继续开发；无需依赖个人记忆。
- 已知问题和未完成范围透明，不假装“永远完成”。

## 最终反馈

提交本阶段完成情况，给出：结构简化的变化与证据、最重要的知识修订、实际测试结果、剩余 `RISK`、新 Agent 的首读路径、旧分支知识同步基线、提交 SHA。不要擅自推送、部署、删除旧分支或宣布旧项目应停止维护。
