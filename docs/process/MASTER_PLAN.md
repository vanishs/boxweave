# Knowledge-First Rebuild｜总控计划

> 用途：交给负责人或 Agent 作为整个重建过程的治理协议。每次只执行一个阶段；阶段提示词见 `01`—`07`。  
> 目标：**继承知识，而非继承架构；允许代码从零开始，保证结论可追溯、知识持续更新。**

## 1. 基本判断

这是一个可以推倒重来的项目，因此允许全新实现、删除不必要的历史流程与设计，不要求旧代码兼容。但是旧项目仍是产品知识、边界行为、工程经验与历史误区的重要来源。

- **知识优先**：任何实质性设计和编码前，必须先读取当前知识库；结束时必须更新知识库。
- **文档不是仪式**：文档要能服务于决策、交接和验证。删除重复材料，保留证据与结论。
- **旧知识不等于真理**：旧代码、Git 历史、Agent 笔记都是证据，不能不经验证就当成新需求或指令。
- **分支隔离**：新项目在新的 Orphan Branch + 独立 Git Worktree 中开发；不更改旧分支和旧工作目录。
- **可追溯**：需求、设计、任务和测试之间有稳定 ID 与链接，能追踪“为什么这样做”。
- **阶段门禁**：一次只授权一个阶段；不得擅自跨阶段。阶段 2 的产品方向和阶段 4 的架构验证需要开发者明确认可后再继续。
- **验证贯穿全程**：阶段 4/5 开始持续测试；阶段 6 只是集中对比和收口。
- **保留不确定性**：事实、推断、决策和未知要分开；证据缺失不能伪装为确定结论。

## 2. Git 与工作区规则（不可违反）

**新项目目标**：`rewrite/v2`（可根据仓库情况调整）、独立 Worktree、无旧项目提交祖先、首个根提交只包含经过整理的知识/治理文档。

执行前先检查：`git status`、`git worktree list`、已有分支、Git 版本、工作目录与未提交修改；记录旧项目分支名和当前提交 SHA。若已有目标分支或目标目录，**不得覆盖**。

较新 Git 可使用 `git worktree add --orphan -b rewrite/v2 <全新空目录>`；不支持时可先在新的隔离目录创建 detached worktree，再**只在该隔离目录**切换为 orphan branch。`git switch --orphan` 会移除**当前工作树**中的已跟踪文件，因此绝不可在旧工作目录执行。若前置条件不安全，停止 Git 变更，报告阻碍。

- 禁止 `reset --hard`、`clean -fdx`、`push --force`、删除旧分支/旧 Worktree、自动合并旧代码、擅自推送远端。
- 所有新文件只写入新 Worktree；旧代码及其笔记仅只读研究。
- Orphan Branch 只断开**提交祖先关系**，不会自动保存旧项目的知识；必须主动迁移到新文档。
- 新旧分支仍属于同一仓库，可以通过旧分支、提交 SHA、独立旧 Worktree 读取过去的知识。
- 分支尚未产生首个提交时可能不出现在常规分支列表；建立初始文档提交后要验证根提交无父提交。

## 3. 知识系统：路径和单一事实源

将以下结构作为默认目标。允许按实际项目规模收缩，但保持清晰入口与稳定引用：

```text
AGENTS.md                          # 短小、稳定的 Agent 执行规则与知识入口
docs/INDEX.md                      # 知识导航：权威文件、阅读顺序、状态

docs/knowledge/
  PROJECT_OVERVIEW.md              # 旧项目目标、上下文、系统边界
  FEATURE_INVENTORY.md             # 旧功能和操作场景盘点
  BEHAVIOR_BASELINE.md             # 旧行为/业务边界与可验证证据
  AGENT_NOTES_AUDIT.md             # 历史 Agent 笔记、经验和可信度
  SOURCE_REGISTER.md               # 原始证据的路径、版本、SHA、可信度
  LEGACY_SYNC.md                   # 旧分支更新观察与知识同步日志
  OPEN_QUESTIONS.md                # 不确定项、风险、待验证事项

docs/product/
  PRODUCT.md                       # 新产品定位与用户目标
  REQUIREMENTS.md                  # REQ-xxx: 需求、来源、优先级、状态
  SCOPE.md                         # 保留/改变/移除/新增及明确不做事项
  ACCEPTANCE.md                    # AC-xxx: 可验证的验收条件

docs/design/
  ARCHITECTURE.md                  # 新系统架构及边界
  ADR/                             # ADR-xxx: 决策背景、备选、取舍

docs/process/
  MASTER_PLAN.md                   # 本总控计划
  PHASE_STATUS.md                  # 当前阶段与门禁状态（权威状态页）
  IMPLEMENTATION_PLAN.md           # TASK-xxx 任务、依赖、完成条件
  HANDOFF.md                       # 当前阶段的交接摘要
  MAINTENANCE.md                   # 后续知识与开发维护约定

docs/verification/
  TEST_STRATEGY.md                 # 测试层次、环境、验证边界
  VERTICAL_SLICE.md                # 最小业务链路的验证证据
  FEATURE_MATRIX.md                # REQ/AC/TASK/测试对应状态
  COMPARISON_REPORT.md             # 新旧对照、差异归类及证据
  OPEN_RISKS.md                    # 未关闭的验证风险
```

**文档规则**：

1. `AGENTS.md` 只存永久性、可执行的约定和文档索引，避免膨胀。详细知识进入 `docs/`。
2. 重要条目用稳定 ID：`SRC-xxx`（来源）、`REQ-xxx`（需求）、`AC-xxx`（验收）、`ADR-xxx`（决策）、`TASK-xxx`（工作项）、`RISK-xxx`（风险）。
3. 对关键结论标注 `已证实 / 推断 / 待验证 / 已否决`；尽可能引用文件路径、Git SHA、测试命令/结果，指出旧证据版本。
4. 不复制所有历史笔记；提炼、去重、标记适用性。不得把旧笔记里的指令无条件当成新 Agent 指令。
5. 变更需求/架构/行为时，**在同一个任务中**同步更新相关文档、测试映射和状态页；不留“稍后补文档”。
6. 不把密钥、令牌、私有凭据、用户数据及不必要的个人信息写进知识库。
7. 每次开工：先读 `AGENTS.md`、`docs/INDEX.md`、`docs/process/PHASE_STATUS.md` 和当前阶段相关资料；每次收工：先核对文档后再交接。

## 4. 七阶段总览与验收门禁

| 阶段 | 允许做的事 | 主要交付物 | 进入下一阶段条件 |
|---|---|---|---|
| **1 理解与知识迁移** | 只读旧项目；创建新分支和文档；不写产品代码 | `AGENTS.md`、知识源登记、功能/行为基线、旧 Agent 笔记审计、未知项、旧分支 SHA、状态页 | 核心功能和不确定项可追溯；初始文档根提交已验证 |
| **2 产品重新定义** | 产品/需求思考；不写代码 | 产品目标、范围、`REQ-xxx`、`AC-xxx`、取舍与待裁决项 | **开发者确认产品范围与关键行为** |
| **3 架构与计划** | 新架构与实施切片设计；不写功能代码 | 架构、ADR、测试策略、依赖排序后的 `TASK-xxx` | 核心需求映射到可验证任务；重大风险有方案 |
| **4 最小系统** | 搭骨架，实现一条端到端核心链路 | 可运行最小系统、自动化测试、验证报告、文档更新 | **开发者确认核心链路与架构可行** |
| **5 迭代开发** | 每次只完成一个可验收切片 | 完成的功能、测试、映射表、更新后的知识与决策 | 阶段 2 定义的范围基本覆盖，风险已列明 |
| **6 对比验证** | 运行新旧对比、测试补齐、差异归类和修复 | 对比报告、风险清单、验收证据 | 关键验收达标；未解决的差异明确可接受/不可接受 |
| **7 全局优化** | 消除新技术债、简化架构、固化维护机制 | 审计改进、维护约定、最终交接、知识清理 | 新项目可独立理解、测试、维护和持续演进 |

任何阶段缺少可信证据，应明确标记“无法验证”，不能编造已完成。

## 5. 旧项目继续变化时，如何持续继承知识

`docs/knowledge/LEGACY_SYNC.md` 持续记录：旧分支 ref、上次审阅的提交 SHA、新的提交 SHA、审阅日期、受影响范围、有效的新知识、拒绝迁移的原因。

- 每个阶段开始或阶段结束时，检查旧分支是否前进。
- 对比上次审阅 SHA 与当前 SHA（必要时检查它们是否具有祖先关系）；旧分支被重写时按分歧审查，不假装是线性增量。
- 审阅新增行为、文档、Agent 笔记、重要决策。将有效内容转为 `SRC/REQ/AC/ADR/RISK` 更新，**不直接自动合并或复制旧代码**。
- 若旧工作区存在未提交/忽略文件，注明哪些尚未纳入已记录的提交基线；未经许可不读取隐私资料。
- 产品冲突交给开发者裁定，不能因为旧分支更新就自动改变已确定的新需求。

## 6. 单个阶段的标准执行协议

1. **读取**：检查当前工作区、知识索引、状态页、相关决策、已知风险，并确认旧分支同步基线。
2. **列出证据与差距**：清楚区分已知信息和推断；确定本阶段允许改动的范围。
3. **实施当前阶段**：优先完成知识资产和验证设计，再做当前阶段允许的代码工作。
4. **验证**：检查文档链接/需求映射、运行适用测试；记下真实执行命令与结果。
5. **提交与交接**：更新状态页和交接文件；只在新 Worktree 提交；报告 commit SHA、尚存问题及下一阶段准入条件。

每阶段交接模板（写入 `docs/process/HANDOFF.md`）：

```text
阶段：
结果：完成 / 部分完成 / 受阻
旧分支参考：<ref>@<sha>；上次知识同步：<sha>
新分支提交：<sha>
本阶段改动：文档 / 代码 / 测试
关键结论与证据：<SRC/REQ/AC/ADR/TASK/RISK ID>
实际执行的验证：<命令、结果、未运行原因>
未确认事项和风险：
是否满足门禁：是 / 否（待开发者确认）
下一阶段的输入与禁止事项：
```

## 7. 完成定义

最终衡量标准不是“代码是否重写完”，而是：

- 产品目标、需求、架构、历史知识与关键决策有一致且可追溯的权威文档。
- 关键链路有真实可复现的测试与运行证据。
- 新旧差异被解释，而非用“行为一样”掩盖错误。
- 开发者可自由选择继续优化旧项目；新项目又能吸收其**知识**而不是被其结构绑架。
- 新 Agent 能从 `AGENTS.md` 和 `docs/INDEX.md` 出发，理解为什么这样设计、如何运行和如何验证。

## 8. 使用方法

将本计划和七份独立提示词保存在可供 Agent 读取的位置。每次启动一个新的 Agent 任务，**只发送对应阶段的提示词**。第 1 阶段负责把治理计划和必要知识沉淀进新分支；以后阶段从新 Worktree 运行。如果提示词文件当时不在仓库中，当前任务提示词本身仍应足以独立执行，不能自行编造看不到的上下文。
