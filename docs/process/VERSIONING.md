# v1 versioning and publication

Read [current status](../STATUS.md), [VERSION](../../VERSION) and [stable selector](../../V1_PUBLISHED_RELEASE). VERSION, merged code and built artifacts are not publication. RC publication is not stable v1 or deployment authorization.

Owner scheme: 1.X.Y (X feature, Y patch), prerelease v1.X.Y-rc.N. Merge to protected v1 only after applicable exact checks and native evidence. For an authorized RC create release/v1.X.Y-rc.N from exact v1 head. The [release workflow](../../.github/workflows/v1-release.yml) builds dual architectures, runs source and isolated installed Scoped N2/S2.5 gates, verifies the 72-marker S2 crosswalk against exact release-run evidence and the candidate amd64 digest, binds the tested manifest checksum, checks v1 head/tag/asset identity and publishes immutable prerelease assets. Do not republish an existing tag or advance v1 while the exact-head release gate is using it. Confirm actual Release and assets. Stable requires distinct reviewed candidate, reconciled evidence, required trusted signatures and owner authorization.

Before formally supported v1 or separate owner compatibility promise, do not add speculative migration layers for obsolete prerelease data/API/role fixtures. Notify users of exact incompatibilities; preserve original UNKNOWN, auth and native evidence; no silent reset/adoption/downgrade. Scoped fresh install, full retirement and reviewed completed-data purge only; historical Legacy installation and upgrade are unsupported. Future stable upgrade/rollback is a separate owner decision. Issue fresh credentials and verify authenticated discovery after recreation. See [maintenance](../getting-started/MANUAL_INSTALL.md), [acceptance](../verification/ACCEPTANCE.md), [quality](QUALITY_GATES.md), [history](../history/README.md).
