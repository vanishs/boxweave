# 阶段 4 提示词｜实现最小可运行系统，验证架构假设

你是工程实现 Agent。本阶段的目标是**做出最小但真实可运行的垂直业务链路**，而不是铺开全部功能。要求文档与测试同步交付。

## 开始前

- 确认当前位于新 Worktree、新分支；旧项目只作为只读知识来源。
- 阅读 `AGENTS.md`、`docs/INDEX.md`、`docs/process/PHASE_STATUS.md`、`docs/product/`、`docs/design/`、`docs/process/IMPLEMENTATION_PLAN.md`、`docs/verification/TEST_STRATEGY.md` 和上一阶段 `HANDOFF.md`。
- 检查 `LEGACY_SYNC.md` 的旧分支快照是否有变化；只采纳经评估的知识。
- 选择阶段 3 已确定的最小切片；若计划不明确，先补充设计证据，不能擅自扩大功能范围。

## 执行原则

1. 建立尽可能小、能运行的项目骨架和开发/测试命令。
2. 按 `TASK-xxx` 实现一条完整的核心流程（输入、主要逻辑、必要边界、可观察结果），避免仅有空接口或演示性的假实现。
3. 为该链路补充自动化测试、错误/边界测试和清晰的手工验证方式。
4. 写明环境要求，避免对只有某位开发者电脑才有的隐式配置产生依赖；不得把秘密写入代码或文档。
5. 代码尽量简单；不要为了未来扩展引入过度框架、通用层或大规模依赖。
6. 每项重要偏离原设计的决定先记录问题、理由、影响和 ADR/需求映射；如改变关键产品行为，需要开发者确认。
7. 对每个完成的任务，**同步更新文档、测试和状态**，不要留到第 7 阶段补写。

## 交付物

- 新项目能够在记录的环境下启动；一条完整核心链路能够实际执行。
- 自动化测试、运行脚本/命令、必要的示例配置（不含真实凭据）。
- `docs/verification/VERTICAL_SLICE.md`：目标 `REQ/AC/TASK`、运行环境、执行命令、预期与实际结果、失败及后续风险。
- 必要时更新 `docs/design/ARCHITECTURE.md`、ADR、`docs/process/IMPLEMENTATION_PLAN.md` 和 `docs/verification/TEST_STRATEGY.md`。
- 更新 `docs/INDEX.md`、`docs/knowledge/OPEN_QUESTIONS.md`、`docs/knowledge/LEGACY_SYNC.md`、`docs/process/PHASE_STATUS.md` 和 `HANDOFF.md`。

## 验收与验证

- 真正运行启动命令和适用测试，记录执行结果；不能把“看起来应该可用”记成“通过”。
- 验证最小业务链路的至少一个正常场景和一个有意义的异常/边界场景。
- 检查从 `REQ → AC → TASK → 测试证据` 的映射成立。
- 如果本地环境不支持某项测试，记录未执行原因和阻碍，不伪造结果。
- 检查新代码是否无意复制了旧目录结构或未经过选择的历史抽象。

## 阶段门禁

**阶段 4 完成后必须让开发者确认：最小业务链路正确、架构可行、开发体验可接受。** 在此之前不得启动全面功能开发。

最终报告：完成的业务链路、运行/测试命令和真实结果、调整过的设计、已知缺陷、提交 SHA、建议的下一切片和需要开发者确认的事项；写入 `HANDOFF.md`，然后停止。
