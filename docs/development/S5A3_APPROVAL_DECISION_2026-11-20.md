## Recommended mechanism (proposal)

Use a narrowly scoped independent HTTPS browser approval route on the existing configured OAuth public origin, not a new service or management Tool. Reuse the existing local high-entropy OAuth approval password verifier (Argon2id), rate-limits, origin and protected form pattern; never reuse an OAuth grant as action consent. The human enters the password directly in their browser, never in chat, Tool arguments, a guest or agent-accessible files. Security assumption: the approving credential is controlled by the trusted owner independently of MCP Agents. If compromised or shared with an Agent, this mechanism cannot establish independent approval; rotate it or use the existing Host root fallback. No new public origin exposure authorized.

A logical release request is admitted only for an exact eligible UNKNOWN original by the existing `operation_recover` Tool. Return a durable pending request identifier and configured-origin approval link, never a bearer secret or credential. User page shows the actual server-resolved original action, Layer, UUID/incarnation, evidence summary, exact proposed release and remaining uncertainty, and explicit approve/deny. GET has no mutation; authenticated same-origin POST records decision. The link alone, ordinary bearer, claimed reviewer, MCP UI confirmation or Elicitation accept cannot approve. Existing SDK feasibility experiment demonstrated a synthetic client can return accept without the user. Elicitation or normal link presentation is optional UX, not proof.

After browser approval, the authenticated requesting Actor can check/resume the same request. Reobserve exact native state, revalidate original snapshot and current service credential/Actor; consume approval, record release audit and separate recovery receipt in one SQLite transaction. Original UNKNOWN outcome, native ID and original idempotency key remain unchanged; only its specifically eligible claim is released. Reject stale or revoked work, and never re-dispatch original. Exact same-key receipt replay works after lost response/restart; changed intent or reused approval for another effect fails. Pending/requested, denied, expired, stale, approved, consumed states must be durable, bounded and audited. Bind request to original ID/intent hash, Layer, Actor, recovery action/key digest, identity, fingerprint, credential epoch and deadline. Do not put passwords, raw approval secrets, or guest data in receipts/logs/URLs.

Proposed allowlist starts with narrowly reviewed ordinary owned-box claims; unbound Create, missing/mismatched UUID, ambiguous network/PRS/Forward/dependent Delete and GC-specific review must not become generic unlock paths. Per-domain re-observation and barriers govern release even with valid approval. Preserve existing local root-reviewed CLI fallback. No new role model, arbitrary host maintenance, original replays or new MCP tool.

Exact fields, existing ledger compatibility path, concurrency constraints and tests to be reviewed before code changes.
