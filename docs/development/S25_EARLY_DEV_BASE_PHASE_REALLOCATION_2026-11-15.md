## 4. Operating envelope after scoped S2.5 acceptance

**Permitted:** owner-controlled development-only use of one dedicated L0, one trusted L1 controller and one L2 Box, pinned and attributable versions, real authenticated MCP, supervised Guest/Git/Test work, limited resource budget and known native fallback. Current six-layer experiments are **observations**, not an authorization to expose six recursively nested controllers to untrusted users.

**Not permitted as claims:** strong per-depth AppArmor namespace, nested device BPF enforcement, hostile multi-tenant/sibling isolation, collision-free arbitrary recursive UID/GID mapping, hard disk/spool quota without proof, unattended OAuth-refresh-safe exactly-once, automated recovery/unlocking of historical UNKNOWN, release-quality HA, stable public service. If any of these is required for the planned actual dev host, **its S2.5 targeted gate fails and the workload must be reduced or blocked**, not magically relabeled PASS.

**Safety invariants:** no host AppArmor disabling; no privileged/unconfined child; no host Incus socket delegation; no unapproved physical-host effects; no foreign Project modification; no direct shell to host as a public Tool; no changing published RC6; no recovery or deletion of historical L0/L2 UNKNOWN. No SELinux work planned. An inherited enforcing AppArmor label may be documented as a **single trusted-tenant compatibility limitation**, never an independent child policy namespace.
