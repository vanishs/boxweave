## Practical findings / how to revise implementation

1. **Mode-specific feasibility:** do not blanket-block nesting. Legacy exact activation refuses generated /run/systemd/system/service.d/zzz-lxc-service.conf; effective NoNewPrivileges=no, ProtectControlGroups=no. Scoped installation and authenticated N2/N3 actual functional tests succeeded despite that inherited environment. Both uninstaller modes reject unreviewed drop-ins before effects, even the healthy scoped empty plan. Never remove/alter this drop-in to force acceptance. Real full retirement/restore/purge/resume and Legacy full activation require the independent clean Ubuntu VM CI lane unless a separately reviewed supported environment is available. H1 must expose all blockers and distinguish runtime health from maintenance readiness (Doctor healthy is not proof of uninstallability). H3 should identify expected nonroot limits without classifying them as a proven fault.
2. **Installation exclusivity:** native_fresh_ipv4.go explicitly requires exactly default + dedicated Project and empty all-project instances. A benign extra empty Project reproduced the refusal twice. H1 should report scope and precise prerequisite; distinguish a legitimate unrelated resource from actual ownership conflict. Do not silently remove foreign resources or loosen exclusivity; existing product supports exclusive bootstrap. A broader shared-host install policy needs explicit design and proof, not just changing a count.
3. **Historical compatibility:** RC13 stock wrapper lacks --guided-full-plan; RC14 source guided preview works with RC13 verified binary but later retirement reader might be absent. Test exact historical wrapper/binary and new coordinator as separate cases, pin schema/identity; never replace staged older binary just to obtain a reader. User's actual #187 unknown revoke was not re-created in lab A because controller activation failed. Use bounded synthetic source fixtures for failure stages plus exact native VM evidence, preserve original historical issue.
4. **MCP user experience:** an outer Exec with a 15-character key returned generic invalid admission; source internal/state/store.go Admit requires length 16..128. Corrected caller input succeeded. A second Exec while original apt operation was VERIFYING returned generic original unresolved resource claim is still locked; original finished, no forced unlock or replay. Busy wait is not a system failure. H4 should add input schema/description constraints and typed safe wait vs UNKNOWN/fault navigation, while retaining non-enumerating auth/foreign denial and same 23 public tools. H3 should reuse underlying typed observations.
5. **Real network limits:** source churn tests and live N2/N3 prove current scoped retention, not safe reuse. H4 can repeatedly exercise lifecycle and directional packets in lab B; 1024/8192 scale is ledger-synthetic, not 1024 physical guests. Design bounded proof for reclamation separately; no automatic reclamation/reset or CIDR expansion without explicit reviewed policy. Capacity reporting fixes do not solve churn exhaustion.
6. **Practical source iteration:** lab A has verified source/toolchain and warm module/build cache. First apt/source/Go compile can be long; separate preparation steps and poll original IDs. Never start competing Exec on the same Box while a mutation remains verifying. Use short focused test selections then full phase tests, and keep each mutation key >=16 chars. The current staged RC13 fixture is not a clean installation target.
