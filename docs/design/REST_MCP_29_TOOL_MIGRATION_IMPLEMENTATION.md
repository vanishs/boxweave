## 1. Executive engineering conclusions

1. **All 29 are in scope for one development program:** **20 semantically read-only** operations (including `compose_discover` despite its HTTP POST) and **9 state-mutating** operations; **8 P1 + 21 P2** by the prior priority matrix. All 29 have upstream REST route definitions; this is a source finding, not proof of a working endpoint, permission, complete data, or equivalent behavior on an installed host.
2. **Two outbound consumers, not one:** (A) app/Web worker calls via `bwmini/provider.py`, `access_provider.py`, `auto_sleep.py`, `box_debug.py`; (B) Agent SSH/HTTP inbound MCP through standalone `bwmini/mcp_gate.py`, which today forwards these upstream tool names to Containarium MCP. Building only (A) would **not** complete the owner-requested 29-tool outbound migration. Agents **continue to see/use MCP**; only the BoxWeave-to-Containarium outbound hop is selected for REST.
3. **Upstream MCP often already calls these HTTP endpoints internally:** e.g. `internal/mcp/client.go` uses `GET /v1/network/guard`, `POST /v1/network/passthrough`, `GET /v1/security/findings`. The main benefit is one **typed, observable BoxWeave-owned transport boundary** and eliminating repeated subprocess/catalog/text parsing for selected calls; it does not automatically add capabilities.
4. **Current REST transport is too narrow for 29:** `bwmini/provider_rest.py:RESTClient.request` requires authenticated loopback, exact private token, no redirects/retries/proxies, supports GET/POST/PUT/DELETE, rejects every `?` in paths, caps request JSON at 64 KiB and response at 512 KiB, and treats every non-GET as a write. It must gain safe typed query support, **operation-semantic** classification, per-route response/error validation and bounded result handling. The existing lifecycle REST contract and its disk-shrink check must remain intact.
5. **Standalone Gateway packaging/trust is a first-class deliverable:** `mcp_gate.py` is shipped as root-managed standalone stdlib scripts in `online.RELEASE_FILES`; it is run as the restricted `boxweave` SSH account by a forced command or in the independent HTTP MCP relay. It cannot assume app-package imports or access to app config/credentials unless explicitly provisioned and validated. Adding an app-only `RESTClient` import to this process would break installed deployments.
6. **P0 precondition for nine writes:** currently the shared R-04 operation coordinator is **opt-in and globally PARTIAL**. Protected Gateway mode intentionally hides and rejects most forwarded upstream tools: `gateway_protection._UPSTREAM_READ` is currently only list/get/system info. A direct REST rewrite must **never bypass** that policy; reclassified read tools and protected tracked-write routes require separate, explicit reviewed coverage. A REST 2xx acknowledgment is not a verified effect. A post-dispatch timeout is **UNKNOWN, retain claim, never retry or silently fall back to MCP**.

### 1.1 Explicit scope / non-goals

- **Included:** 29 typed REST implementations, two outbound paths where the tool is exposed, response/identity parity, safe query construction, capability probing, classification and trace events, protected-mode integration, source tests and approved isolated live acceptance. Existing Web business intents/receipts and existing Agent MCP input schemas remain the user-facing contracts.
- **Not included:** converting inbound Agent MCP to HTTP REST, removing upstream MCP for the other 39 visible tools, rewriting `connect(exec)`/SSH/agent-box, adding general Web APIs or unrelated UIs for Gateway-only tools, converting backups/snapshots, changing Provider minimum versions, repairing upstream incidents, enabling protected policy on the owner host, altering stable installer pins.
- **Do not create unused Web endpoints just to count a migration.** A tool with no current Web caller is implemented in the **Agent Gateway selected REST route**, plus a reusable typed client if appropriate, not a speculative application UI.
- **Do not treat Gateway upstream MCP forwarded `tools/list` as REST authorization.** Its schema informs compatibility, not access grants. Existing host-wide tool allowlist and read/privileged policy apply *before* any dispatch.

### 3.1 Shared library and installed-process design choice

**Preferred design for this program:** one small **pure-stdlib, standalone-safe HTTP transport module** (name to be determined during implementation) with a typed route registry. The app `provider_rest.RESTClient` and standalone Gateway use **different thin authorization/identity facades** over that lower-level transport. Avoid importing `bwmini.__main__`, application `Store`, or Web sessions into the Gateway. Keep the existing `RESTClient` public lifecycle methods and fixture injection stable.

Before enabling Agent REST traffic, positively establish the gateway process UID, private token-file owner/mode, effective API principal/scopes, approved `127.0.0.1` port, and exact backend/project binding **on an isolated installed host**. App config/credential visibility to Gateway is *not* inferred merely because both have a `boxweave` account. No root-held signer or raw JWT should be copied into project artifacts, logs or test responses. Absent or mismatched binding **fails closed to an explicit unavailable outcome**. Do not silently fall back to MCP after a REST request may have been sent.

If source/package constraints prevent safe sharing, an explicitly bounded **Gateway-only** HTTP implementation is preferable to breaking the installed forced-command path. Duplicating the complete app service, bypassing the Gateway or allowing an unrestricted URL/proxy is **not** acceptable. Update `online.RELEASE_FILES`, managed public copy list, build manifest, dependency audit and ARCH-0 standalone import tests together.

### 3.2 Typed HTTP request/response constraints

1. **No arbitrary URL:** endpoint is immutable configured loopback origin; route is selected from a fixed enum, path variables individually type-validated and percent-encoded with `safe=""`, query keys drawn only from an endpoint-specific whitelist via `urlencode` and bounded lengths/counts. No redirect, proxy, path traversal, scheme change, userinfo, query-in-route input or credential-bearing logs.
2. **HTTP method is not the business-effect classifier:** `compose_discover` is a **read despite POST**. The nine exact write names are the exclusive default-deny mutator registry. Unknown/new upstream tools have *no* implicit REST write rights. Preserve current `GET/POST/PUT/DELETE` support; no PATCH needed for the defined 29.
3. **Structured results:** decode JSON with duplicate-key rejection, response limits, exact expected top-level fields, enum/version checks, strict types and route-specific optional values. `get_backend` filters the full authenticated list locally. `security_findings` gathers three scanner sources and normalizes names/risk/suppression/container filtering and protobuf JSON int64-as-string; one scanner failing is **partial** with explicit source status, never empty/full success.
4. **Complete lists:** pagination/incomplete-backend signals and excess rows must raise `not_verified/incomplete` or retrieve within approved bounded cursors; truncation cannot become a valid empty/complete result. A 512 KiB limit is a **safety bound**, not evidence that the full inventory fits.
5. **404 semantics:** an authenticated exact `GET /v1/network-policies/{tenant}` can mean an *absent tenant policy* only when the daemon's expected NotFound contract is positively recognized; do not confuse it with a missing HTTP route or lost backend. Missing Box, backend ID, route and tool must each map to their own typed meaning. Avoid raw upstream exception text in logs or Web.
6. **Error/timeout:** pre-validation and unreadable credentials are definitely pre-dispatch; after request handoff, **every ambiguous write outcome stays UNKNOWN**, including HTTP error responses lacking an independently established no-effect guarantee. No retry by HTTP libraries, workers, Gateway or a cross-transport fallback. Reads may be reattempted within bounded policy but may not be used to infer write side effects automatically.
7. **Auth and scope:** `tools/list` and signed-in upstream MCP capabilities **do not establish** direct REST JWT permissions. For each selected endpoint, separately record authenticated allow/deny/expired-scope observations, target tenancy, service UID, configured Provider identity and error redaction. No new per-Agent RBAC claim.

### 3.4 Safe cutover and fallback state machine

- **Unconfigured / legacy:** keep existing Web option and Gateway MCP semantics; no implicit switch because Provider >=0.128.0.
- **Preflight-only:** inspect selected local REST URL/version/response shape and permissions without executing mutations; auth failure, unsupported routes or insufficient scope => **REST_NOT_ELIGIBLE**, preserve existing configured path.
- **Read canary:** selected **20 reads** use direct REST in a disposable isolated deployment; compare normalized results with MCP for the same exact target/time window. Mismatches must be classified (scope, eventual state, enum, pagination, projection) rather than suppressed.
- **Write canary (isolated, explicit authorization):** selected **9 writes** use a single chosen transport and a durable `dispatch_intent`. If dispatch could have occurred, timeout/lost response => UNKNOWN and **no REST -> MCP retry**. Live observation of the original operation is necessary.
- **Promotion:** opt-in via reviewed source-bound configuration **per operation/endpoint**, not one unconditional `REST_FIRST=true` environment toggle. Preserve old configs on upgrade. Protected Gateway mode remains restricted until every newly exposed read/write meets policy requirements.
- **Rollback:** disable **new future dispatch** for a selected tool without erasing in-flight/UNKNOWN receipts, claims or provenance. Existing reconciliation must continue against the original target with read-only observations; never recover by replay, claiming a different incarnation, or deleting an unowned resource.
