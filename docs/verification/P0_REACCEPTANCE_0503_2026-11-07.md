## Follow-up code and Gateway-log root-cause investigation (2026-11-07 UTC)

**High-confidence common-cause hypothesis, not independently verified host-journal root cause:** the **root-published target/SSH-trust registry freshness** is shared between create-time R-04 scope attestation and Agent `connect`. A scanning stall on the installed owner host can cause an early create rejection **before REST POST**, which the HTTP wrapper currently misclassifies as UNKNOWN.

### Source-proven chain and observed correlation

1. `bwmini/hostkeys.py:32–75` refreshes `/var/lib/boxweave-default/public/targets.json` **only after** enumerating the full Incus inventory and running up to **three sequential** `incus exec <Box> cat /etc/ssh/ssh_host_*_key.pub` operations for each eligible RUNNING Box. Each subprocess has a **15-second timeout** (`hostkeys.py:9–10`). No per-Box independent checkpoint or in-progress freshness update is published.
2. `bwmini/online.py:933–942` provisions `boxweave-trust.service` and `boxweave-trust.timer`, with `OnUnitInactiveSec=15s`. This interval starts after each oneshot service exits, **not** while it is executing; a slow/failed scan can leave the previous registry in place for substantially longer.
3. `bwmini/coordination_bridge.py:37–53` **requires** `0 <= now - targets.observed_at <= 45` for `published_scope()`, rejecting with `COORDINATION_SCOPE_UNVERIFIED` if stale.
4. `bwmini/gateway_create.py:209–229` calls that `published_scope()` and acquires the shared R-04 claim **before** the only outbound `POST /v1/containers` at line 230. If the scope is stale, it freezes the already reserved task and raises `REST_CREATE_PREDISPATCH_UNVERIFIED` despite **no POST by this code path**.
5. `bwmini/remote_mcp.py:422–455` maps an unsuccessful Gateway JSON-RPC response to `journal.complete(task, False)`, producing `unknown / UPSTREAM_CREATE_OUTCOME_UNKNOWN` **without distinguishing definitely pre-dispatch refusals** from post-dispatch lost acknowledgement.
6. `bwmini/mcp_gate.py:426–432` reads the **same** `targets.json` registry and returns `TRUST_OBSERVATION_STALE` when the same 45-second threshold is exceeded. Real Agent `connect` on newly RUNNING `bw-p0-0503-1107-b` returned this exact code.
7. `bwmini/gate_diagnostics.py:39–50, 162–172` does not whitelist any `create_container` local denial for deterministic FAILED classification, so **even a local pre-dispatch JSON-RPC rejection is logged as `UPSTREAM_JSONRPC_ERROR`**. The two live traces cannot, by themselves, prove the error originated upstream.

The current live Provider inventory has **45 RUNNING Boxes, all with conventional `-container` names and private IP addresses**. Assuming they are all eligible in the native Incus list, the host-key publisher can execute **up to 135 sequential** `incus exec` reads per sweep (plus listing). At an average >0.33 seconds per key read, a single scan already takes >45 seconds, and `OnUnitInactiveSec=15s` creates an additional gap. Some Boxes may be skipped (e.g. missing Incus marker or host key); this count is a capacity bound, **not measured execution timing**.

This explains both fresh nesting-enabled requests becoming UNKNOWN **without observed Box instances** and the independent new Box `connect` reporting stale trust. It does **not prove** the stale scope was the specific error for both historical trace IDs, because the exposed Gateway diagnostic records intentionally omit the underlying classified local code and host journald is not exposed to the Agent. Do not attribute causality to `enable_nesting` itself based on this three-request sample. Direct nesting change is **only post-accepted-create**, via `bwmini/async_create_observer.py` and the exact Incus `security.nesting` helper (`bwmini/nesting.py:61–90`). The v0.50.2 synchronous legacy gate likewise performed `nesting_plan` and `nesting.apply` only following a successful create reply (`bwmini/mcp_gate.py:933–942, 1032–1050`).
