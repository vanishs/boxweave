## Reproduction and corrections

1. **Unpatched official local CLI bug — REPRODUCED.** `containarium create bwlab-cold --no-ssh-key --idle-stop 1m` returned exit `0`; Incus recorded `auto_sleep_enabled=true`, `idle_threshold_minutes=1`, but **no `user.containarium.last_started_at`**. The Box later did sleep because it had a recorded network-activity signal; this does **not** prove the quiet/no-signal case safe. The local `internal/cmd/create_local.go` path had missed the clock initialization added to server `CreateContainer` by #3474.
2. **Local CLI fix — S+L PASS.** New helper stamps UTC RFC3339 `LastStartedAt` **before** enabling the policy, and never enables on clock-persistence error; `--idle-stop` remains explicitly opt-in. A separately compiled patched CLI (`301fcbc99150bdba74569d3b64ced5f2806f34cef6300fcd18dcb83ea1dbe3db` SHA-256) created `bwlab-patched`, exit `0`, with `last_started_at=2026-11-03T08:09:05Z`, enabled=true, threshold=1. The real daemon auto-sleep ticker later stopped that Box at **08:12:40 UTC**, without manual Stop.
3. **MCP birth-create gap — S+L PASS on fork patch.** Official upstream MCP `create_container` did not expose `idle_stop_minutes`, though daemon REST/protobuf and CLI already support it. The follow-up adds an **optional** non-negative integral `idle_stop_minutes` field to the MCP JSON schema and forwards it to REST as `idleStopMinutes`. Invalid/fractional/overflow inputs and contradictory `disable_auto_sleep=true` are rejected; omission preserves the previous default. Compiled MCP server SHA-256: `0594252de3c3fc78e10d4c79ccba4c5f8c23fd1399f4204fca356b72562f096f`. Actual stdio MCP `initialize → tools/list → tools/call(create_container)` created `bwlab-mcp` with opt-in 1 minute. Incus independently showed start clock `2026-11-03T08:18:09Z`, enabled=true, threshold=1; the daemon ticker stopped the Box at **08:21:40 UTC**. The first attempt correctly refused an insecure HTTP REST endpoint; the successful test used an explicit **lab-only loopback HTTP opt-in**, not a change to production MCP defaults. An explicit test public SSH key was supplied; no private key or JWT was exported.
4. **HTTP wake route 1 — L PASS.** `bwlab-wake` ran a real systemd Python HTTP app on port **8080**. Authenticated daemon toggle `scale-down enable --idle 1m` stamped `LastStartedAt`; the daemon stopped it by its own ticker at **08:06:40 UTC**. Before the request, independent Incus showed **STOPPED** and the Caddy upstream had switched from Box IP to the local wake handler. The **first** request through Caddy for `probe.wake.lab.invalid/wake-proof.txt` returned **HTTP 200** in **1.607 seconds**, exact body `WAKE_MAIN_LIVE_1103`; independent Incus then showed **RUNNING**. No intervening manual Start.
5. **HTTP wake route 2 — L PASS.** The same Box also ran a different app on **8081**, mapped to `probe2.wake.lab.invalid`. It again **automatically stopped** at **08:09:40 UTC**; Caddy switched the second route to the wake handler. The next first HTTP request to the second route returned **HTTP 200** in **1.591 seconds**, exact body `WAKE_SECOND_LIVE_1103`, and the Box returned to RUNNING. This proves two distinct target ports across separate real wake cycles; it is **not** a simultaneous multi-route race test.
6. **Security boundary.** The isolated daemon explicitly limited wake trusted proxies to its own local Caddy-facing bridge address (`10.59.68.1/32`; loopback is implicitly trusted). A direct attempt from another nested guest to the daemon port was blocked by native guest networking before reaching the wake handler. Therefore a fresh **HTTP 403 negative from an untrusted independent guest was not verified** on this exact runtime; do not inherit the previous v0.126.0 report's 403 proof as new v0.127.0 evidence.

## Follow-ups and release boundaries

- **Upstream:** owner must open a follow-up PR from the fork branch above. Both local CLI birth-clock correction and optional MCP birth opt-in are **unmerged**. Do not present the fork patch as part of official v0.127.0 or current upstream main.
- **BoxWeave:** current MCP gateway passes discovered Provider tool schemas through, but its **Web lifecycle create adapter does not yet accept/forward a birth idle-stop setting**. The direct upstream MCP creation capability becomes usable only after this follow-up is merged/published and an appropriate Provider is installed; current host `0.120.1` has not gained it. Preserve default-off policy and explicit confirmation semantics; do not silently enable auto-sleep on existing Boxes.
- **Environment:** this is a narrow nested Linux live test, not the entire E2/E3/E4 installed upgrade gate, production migration, session-activity safety proof, distributed-provider test, concurrent multi-agent test, or external HTTPS acceptance. The earlier [v0.126.0 report](CONTAINARIUM_0126_AUTOSLEEP_WAKE_LIVE_2026-11-02.md) remains valid **only for its own pinned candidate and test setup**.
