# BoxWeave v1 RC5 — BH-018-like failure-mode cross-module audit (2026-11-14)

**Audit mode:** static source inspection and existing-test coverage crosswalk only. **No direct L0 crash injection, no new runtime test passed in this audit.** Release `v1.0.0-rc.5` / exact `v1` commit [`1224845c139177f3986d1ca3d51032849422ed1c`](https://github.com/vanishs/boxweave/commit/1224845c139177f3986d1ca3d51032849422ed1c). Main invariant: **no potentially dispatched Incus effect may be automatically retried after an ambiguous outcome**; original durable result, authorization and postconditions must remain accurately attributable across subprocess crash, DB crash, request/ACK loss, timeout, OAuth token rotation and safe restart. `SUCCEEDED` for BoxWeave native Exec is not proof of successful Guest command; Guest `exit_code` / `command_success` are separate.

## Actionable test specification (in priority order)

1. **P1 / OAuth continuity:** one isolated local grant G, access A with token ID a; send an authorized `box_exec` with key K, ensure `SUCCEEDED` and one Guest side-effect; rotate **same** grant G to access B/token ID b. Invoke exact same key/intent with B; desired result `duplicate=true`, same original BW & native IDs, no new Guest effect. Separately verify refreshed viewer's authorized prior receipts/streams; unrelated grant G2 with same key/work_ref must **not** borrow G's original; revoked old token cannot act. Do not force client credentials or access L0 tokens. **Expect this requirement to fail on current RC5**; that outcome is the bug proof, not a reason to weaken per-tenant isolation.
2. **P1 / Delete boundary:** construct an independently owned one-use SQLite ledger with exact `box_delete` original in `VERIFYING`, actual verified native delete or controlled typed Oracle; kill the isolated worker after `TombstoneOwnedBox` commit but before generic `Verified`. Reopen the DB, call `Recover`; assert original ID/native ID unchanged, `UNKNOWN` lock, no reissued DELETE, tombstone retained; verify manual local recovery requires explicit review. Then write/fault-test atomic `FinalizeVerifiedDelete` to close that DB transaction gap without changing original receipt semantics.
3. **P1/P2 / Create boundary:** same for `RegisterCreatedBox` → `Verified` and `VerifiedFailed` with residual STOPPED Box; preserve ownership/name lock until evidence-backed cleanup; ensure fail/rollback paths are atomic.
4. **P2 / Native finalizer parity:** per-action response mismatch and 5s native-operation expiry, HTTP 202 lost ACK, pre/post-SQLite ACK loss and independent native postreads. A short-lived terminal 404 is **never** proof of absence or authorization to redispatch.
5. **Scope controls:** source/unit tests first, then installed HTTP MCP on disposable signed Incus VM (T+I+N+V). Never use L0/service SIGKILL, host AppArmor/privilege changes, overwrite existing Boxes, or replay historical UNKNOWN. `v1` stable RC5 binaries remain untouched until reviewed code, unit tests and isolated full gate succeed.

## Design choices needing review

- **Do not naively switch OAuth `TokenInfo.UserID` to GrantID**: `Worker.Claim` and `RequireActiveTokenID` use ephemeral token credential identity for revocation; `GetScopedOperation`, `Replay`, `Admit`, audit and role/scope authorization need an explicit safe split between stable grant-bound actor vs current valid token ID. Manual Bearer tokens can retain current per-token identity. Existing original receipts in SQLite must not be silently re-parented; review backward-compatibility for already-installed test state. This is particularly important because a normal OAuth refresh *intentionally* revokes the previous access token.
- For Create and Delete, the **native effect cannot be part of a SQLite transaction**, but after independent original native outcome verification the relevant *internal DB rows* can often be finalized together. Account for genuine failed Creates leaving a still-OWNED stopped guest and rejected/UNKNOWN cases; do not merge verified failure into success.
- The original `Incus Operation` lifetime is outside BoxWeave's control. A robust improvement must preserve exact original identity and accept an explicit `UNKNOWN` when no provable postcondition exists; unobserved 404 is never evidence of success or failure.

## Caveat / outcome

**Source-level conclusion:** One high-confidence **authorization-identity/idempotency interaction** (X-01) that can defeat same-grant retries across OAuth refresh, two confirmed non-Exec split-transaction windows (X-02/X-03, currently fail-closed), and limited provenance/terminal availability gaps (X-04/X-05). No new same-credential Exec 126/127 unsafe replay was found in the examined RC5 source. **No unsafe real-world duplicate Guest execution has been demonstrated by this static scan.** Issue #148 tracks the top priority. This document is an **audit hypothesis matrix**, not a completed new installation or acceptance.
