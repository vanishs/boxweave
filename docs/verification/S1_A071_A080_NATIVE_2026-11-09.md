## A-071 — real separate-filesystem storage adversarial tests

The initial `1.0.20-s1-exit` reader checked `GetStoragePool.Status=Created` but not backing storage. In the disposable guest, temporarily unmounting the directory source `/mnt/s1-a071-probe` left the Incus pool `Created`, and the old doctor incorrectly returned `ready=true`. The test mount was restored. **This is a real test witness, not a fake SDK error.** Note that Incus also retained a separate canonical pool mount during this specific source-only unmount; an immediate native read may still work, but persistent source health is not thereby proven.

Implemented `internal/native/storage_filesystem.go` and updated `internal/native/status.go`: for actual **dir** pools, independently inspect Incus's canonical `/var/lib/incus/storage-pools/<selected>` path and kernel `statfs` as the **restricted nonroot actor**. For explicitly nondefault dir pools, refuse fallback to the root filesystem when the canonical mount disappears. Inspect real free bytes on the selected filesystem (minimum **64 MiB for basic readiness**, not a promise that an image/Box can fit), rather than substituting host-root capacity. Return truthful `selected_storage_space_checked`, `selected_storage_available_bytes`, `selected_storage_separate_mount` and safe error classes. Official Incus SDK redacts `pool.Config.source` from restricted users, so **this is a canonical-pool readiness probe, not an unprivileged reading of the original source path**. Non-dir storage drivers are not misreported as having statfs-backed capacity verification.
