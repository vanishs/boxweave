## A34 — Newly identified security defect: administrator authorization rate limit

**Source-backed root cause (S, regression added):** `remote_mcp.approve → RemoteCredentials.approve → _rate(db, "admin_authorize", 5) → check_password_hash → RemoteError("access_denied") → Store.db`. In v0.26.5, a rate-attempt insert and the invalid-password exception occurred in the **same SQLite transaction**. The `Store.db` generator catches any exception, rolls back and closes. Therefore denied requests discarded their own throttle attempts and a configured 5/minute limit did not persist for failed password checks. The existing positive OAuth PKCE/refresh fixture could not detect this condition.

**v0.26.6 fix:** Commit the rate-attempt increment in one `BEGIN IMMEDIATE` transaction **before** a second transaction checks the pending grant and fixture password, consumes the pending item and writes the authorization code. The failed grant transaction still rolls back; the limiter ledger does not. The per-minute allowed count, pending expiration, normal approval and token issuance contracts remain unchanged. No administrator credentials were read or used in this audit.

**Required T acceptance:** The added isolated `tests/test_remote_mcp.py` fixture submits denied authorizations using a disposable Store, verifies the attempted authorization ledger contains five committed rows, no authorization code is generated, the next attempt returns HTTP 429, and a valid test approval succeeds once the artificial clock passes the threshold. Existing positive registration/authorization-code/PKCE/refresh/revocation paths and source CI must continue passing. **External real OAuth client over public TLS remains U** and is not inferred from a local Flask fixture.
