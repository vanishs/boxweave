## D4 real user systemd and the exact bug (L PASS)

1. Created **only** task-owned nested `bwd4svc-1102-container`, logical `bwd4svc-1102`, createdAt **1793673230**. Its `systemd-logind`, `dbus-user-session` and `libpam-systemd` were installed. This did not alter the outer host user manager.
2. Created a root-reviewed, user-owned **test-only** systemd unit `boxweave-d4-probe.service` with `ExecStart=/usr/bin/sleep 600`. Using the user's own `XDG_RUNTIME_DIR=/run/user/1001`, the real guest `systemctl --user start/is-active` returned **active / exit 0**.
3. Authentic installed noninteractive `connect(exec)` still sent **no XDG_RUNTIME_DIR**; raw `systemctl --user is-active` returned **exit 1 stderr-only `No medium found`** although the service and user bus were active. Installed **v0.42.7 D4** therefore returned **`not_verified / PROJECT_COMMAND_EXIT_NONZERO / 1`**, proving the old negative was a wrong environment rather than an inactive service.
4. The reviewed v0.42.8 fix changed only **D4's fixed service/log command generator** to prefix `XDG_RUNTIME_DIR=/run/user/$(/usr/bin/id -u)` and use absolute trusted `/usr/bin/systemctl` / `/usr/bin/journalctl`. The shell expression derives the *guest's own UID*; the caller cannot choose the runtime path or command. Existing exact-Box root allowlist, service-name regex, no-output-leak and prior restricted tool surface remain intact.
5. Created a temporary **root-owned exact-name+createdAt** D4 policy only inside the disposable outer Box. ## Real auto-sleep and remaining HTTP wake limit (L/PARTIAL)

1. Created task-only second nested Box `bwsleep-1102-container`, logical `bwsleep-1102`, createdAt **1793673510**, originally RUNNING. Authentic Provider `toggle_auto_sleep(enabled=true, idleThresholdMinutes=1)` returned success and Incus config showed `auto_sleep_enabled=true`, threshold 1 minute.
2. Merely creating the Box did **not** stamp `user.containarium.last_started_at`; with no recorded network activity, it stayed RUNNING even after more than three minutes. The `v0.120.1` upstream `Decide` source explicitly skips idleness when both last-start and network activity are unknown; this is a **real readiness/cold-create limitation**, not proof that the entire auto-sleep implementation is absent. It must be retested on v0.126.0 (do not silently stop/start a real user's Box as a workaround).
3. On **this test-owned guest only**, explicitly called authenticated Provider `stop_container` then `start_container(waitForReady=false)`: both succeeded, identity/createdAt unchanged, and `user.containarium.last_started_at=2026-11-03T02:43:27Z` was stamped. No guest SSH session or traffic kept it active.
4. The actual running `v0.120.1` daemon's **one-minute auto-sleep ticker** logged `stopping username=bwsleep-1102 reason="idle 2m >= threshold 1m (no network signal, since-start)"`. Independently observed authenticated `get_container` **`CONTAINER_STATE_STOPPED`**, proving a real **idle-stop**, not just accepted flag. A manual authenticated `start_container` returned RUNNING with the same createdAt; disabling `toggle_auto_sleep` returned `enabled=false`, confirmed in Incus config.
5. **HTTP wake is not accepted:** the test daemon's `list_routes` returned **`routes: [], totalCount: 0`** and its `boxweave-provider.service` was standalone REST without app-hosting/Caddy route family. Upstream v0.126.0 implements HTTP wake only with configured route hosting/gateway/host IP. No test-owned Caddy/authorized public hostname existed; creating a public route without a separate grant would exceed this task. The manual start proof does not count as request-triggered HTTP wake.

**Disposition:** P-01 actual **auto-idle-stop L PASS with known LastStartedAt precondition**; initial-creation cold-idle behavior remains an OPEN upstream integration issue; HTTP route-wake **BLOCKED by missing configured route/proxy**, not by absence of code.

## E2/E3/E4 exact contract disposition

- Actual authenticated local `Provider.session().discover()` returned **58 MCP tools**; the only matching sleep/snapshot/backup/restore/clone-named tool was **`toggle_auto_sleep`**, while `get_container` existed. Nevertheless the **installed 0.120.1 CLI itself** exposed `containarium snapshot create/list/delete/rollback` plus `containarium backup` commands, proving that the former 'upstream has no snapshots' diagnosis based only on MCP discovery was overly broad.
- Real installed Incus pool was **`driver=dir`**. The snapshot contract in [upstream architecture](https://github.com/FootprintAI/Containarium/blob/v0.126.0/docs/architecture/container-snapshots.md) is **ZFS-backed** and not automatically available for a `dir` pool. **No snapshot or destructive rollback was attempted against unsupported storage.** E2/E3 require appropriate storage, typed authenticated Provider adapter/CLI integration and an independently authorized disposable canary.
- The newly published `v0.126.0` includes **`restore_box_backup` MCP** (encrypted whole-box restore into a distinct stopped target) but no proven whole-box-create equivalent in the current documented `create_backup` MCP schema; use the reviewed CLI `backup create <box> --box` or a typed upstream endpoint after preflight. It is **not** equivalent to same-Box ZFS rollback. Snapshot-source `CloneContainerFromSnapshot` remains **proposed** upstream; an imported/backup-restored copy needs independent SSH/tenant/storage identity/rekey and must not be advertised as fully verified E4 clone.
- **Disposition:** E2/E3/E4 stay **pending Provider integration and correctly provisioned canary**; this task commits only the [future v0.126.0 design/upgrade handoff](../design/CONTAINARIUM_0126_UPGRADE_E2_E4_HANDOFF.md), not an implementation, an upgrade of the owner's Provider or a fake restored/clone PASS.
