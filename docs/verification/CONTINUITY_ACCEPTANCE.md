## Completion and gate rules

- **S2 PASS** requires TC-001–010 (TC-003 now tests a new baseline database and real restart, **not S1 legacy migration**) plus every preexisting S2 A-/SDK-G requirement. Altered S1 admission/SQLite/authorization paths must be reaccepted against the exact new S2 binary. TC-010 may record a **verified no-op** for optional progress UI, but cannot claim an untested notification PASS. A required crash/UNKNOWN test never becomes optional.
- **S2.5 BRIDGEHEAD LAB_PASS/HOST_GO** additionally requires TC-011–014 in their corresponding isolated/approved host context and **all original BH cases**. A disposable lab cannot authorize real-host deployment; no ChatGPT client capability may be guessed. If client cannot send custom `_meta` but accepted fallback works, this is not a security failure.
- **S3/S4 PASS** requires their TC subsets on real installed candidates **and** all original file/network/nested A-case requirements; a valid work label or successful native Exec cannot close unsafe file CAS or host-global Scriptlet/LAN/IPv6 gates.
- **S5 PASS/release** requires TC-019–020, changed-API TC reacceptance on the final exact installed binary, entire 20 MCP Tool + local CLI and independent original A-/BH-/SDK-G release gate. Future MCP Tasks extension remains research-only; absent client/SDK support does not block v1 release, but a **falsely advertised** Tasks extension is a FAIL.

## Safety / privacy / concurrency calibration

Test with distinct tokens on one layer, same token different labels (prove labels **do not** authenticate), retired token vs new token, and a separate nested layer. Include paginated large retained audit history, slow SQLite, concurrent create/delete and stale read evidence. Check no raw guest stdout, prompts, keys, authorization headers or sensitive ids in Tool or shared checkpoint outputs. A client stalled mid-Tool cannot be forced to resume by the server; human “continue” starts with independent verified read, not a replay.
