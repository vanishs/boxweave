## 2026-11-18 multi-Agent Activity design crosswalk (planning only)

**Design link:** [MCP Agent UX + Activity/Evidence overview](../history/development/V1_MCP_AGENT_UX_AND_ACTIVITY_DESIGN_2026-11-18.md). This section **does not** change the already approved TC-011–020 requirements, historical evidence/signatures or original S5 release gate. `box_activity_get` remains **NOT IMPLEMENTED** and the additional public Tool remains **UNAPPROVED** for implementation as of this update.

- **Product intent:** v1 multi-Agent cooperation means **reliable handoff and safe concurrency**, **not** built-in Agent registration, lead/subagent hierarchy, automatic task orchestration, job scheduler, MCP Tasks engine or a BoxWeave checkpoint store.
- **Auth handoff (current Schema v4 / role-free):** A and B authenticate using separately revocable Actor credentials with **no** `admin/viewer` role or OAuth application Scope; they may inspect authorized original Operation receipts **within the same Layer**, but B cannot replay A's original mutation under A's idempotency scope. An OAuth Access Token refresh retains its Grant Actor. Cross-Layer/foreign resources and revoked Token access remain denied; correlation labels never grant authority. Older role-based test records are historical.
- **TC-015 external handoff:** New Agent B checks client-owned Checkpoint (objective, Git HEAD/dirty worktree, original IDs), reads authorized `operation_list/get` and native/Exec evidence, preserves historical UNKNOWN and decides only safe new work. A proposed `box_activity_get` can shorten the evidence-discovery step but **cannot** replace external checkpoint/Git reconciliation, authorize a blind replay, or prove Agent task completion.
- **TC-016 concurrent writers:** Shared Git/Checkpoint requires the external revision store's optimistic concurrency/conflict handling, never silent last-writer-wins. Existing BoxWeave resource claims protect selected native operations, **not** arbitrary concurrent Guest Exec writes to the same Git tree; parallel Agents should use appropriate independent branches/worktrees/Boxes or external synchronization.
- **TC-017/018 and TC-019/020:** Same-work native Peer/Forward/Delete locks and cross-layer isolation remain mandatory. If a separately approved Activity Tool enters the final installed candidate, verify three implemented `overview/issues/evidence` views, correct old UNKNOWN/resource blocker visibility beyond the default recent window, actual independent Actor/Layer visibility and pre-return revocation recheck, truthful native/SQLite evidence gaps, and an intentionally known-bad negative-control failure. This **adds** Tool coverage without replacing original native/physical-network/Verifier gates.
- **Tool inventory:** Historical **20/20** entries below describe the earlier S4-B baseline; the approved S4-C `box_wait_ready` raises the *planned* full inventory to **21**, and **22** only if `box_activity_get` is separately approved/implemented. Final S5 acceptance must enumerate and test **every installed, approved Tool and CLI leaf on the exact candidate**, rather than assuming historical fixed counts.

## Safety / privacy / concurrency calibration

Test with distinct tokens on one layer, same token different labels (prove labels **do not** authenticate), retired token vs new token, and a separate nested layer. Include paginated large retained audit history, slow SQLite, concurrent create/delete and stale read evidence. Check no raw guest stdout, prompts, keys, authorization headers or sensitive ids in Tool or shared checkpoint outputs. A client stalled mid-Tool cannot be forced to resume by the server; human “continue” starts with independent verified read, not a replay.
