# Containarium upstream evidence and reacceptance reference guide

**Status:** curated reference and Agent procedure; **not** acceptance evidence for BoxWeave and **not** an installed automation. Reviewed 2026-11-05 against upstream `FootprintAI/Containarium` tag **v0.128.0** (tag object/source commit inspected), and source HEAD v0.131.0 as an additional drift check. The project uses **MCP-first + REST-assisted** integration; upstream's CLI-first architectural preferences do not override BoxWeave's owner-selected architecture.

**Entry points:** [canonical reacceptance runbook](../process/FULL_PROJECT_REACCEPTANCE.md), [execution development plan](../design/REACCEPTANCE_EXECUTION_ORCHESTRATION_PLAN.md), [action/feature ledger](REACCEPTANCE_RUN_TEMPLATE.md). Always read these first; this guide tells an Agent **where to look upstream and which ideas to apply**, not how to change a production host.

## 1. Pin upstream identity; never cite floating `main` as current installed behavior

- Before an acceptance run, independently record source SHA, installed BoxWeave release/digest and actual Containarium **daemon**, CLI, platform MCP, REST gateway and Incus versions. Different host processes may have different versions. Make the runtime call, not an inference from `go.mod` or a repository document.
- Fetch or read upstream source at the **installed daemon tag or exact digest** (for the current historical baseline, v0.128.0): `proto/containarium/v1/*.proto`, `internal/mcp/*`, `internal/cmd/*`, `internal/server/*`, `internal/client/*`, actual build-target/package metadata. Also compare to the previous installed version and latest upstream for candidate changes, without silently upgrading.
- Every upstream-source assertion must carry `upstream_ref`, source path and whether proven through **source**, **unit**, **real installed CLI/MCP/REST**, or **independent Provider/guest observation**. A matching proto annotation proves a **declared route**, not that the running gateway serves it.
- Link distinct upstream and BoxWeave issue records; a BoxWeave forwarded HTTP 404 is a proven **user-visible failure**, not by itself proof of the failing native component. An upstream version change triggers a new scoped route and capability probe.

## 3. Actual v0.128.0 callability verified during reference research

Read-only probe of the retained isolated Box (`bw-reaccept-1105-b`) found its installed `containariumd version` is **0.128.0**. Its **host/server executable** advertises:

- `containariumd proof-pack generate <owned-container> --dir <reviewed-repo> --out <private-file>`.
- `containariumd proof-pack verify <sealed-pack>` (requires an actual sealed artifact and appropriate audit access).
- Ordinary `containarium proof-pack --help` returns **unknown command**; the client is **not** a substitute for the host-side generator.
- Proto declares an authenticated `POST /v1/proof-packs/verify` for already **sealed** packs. Do **not** invent an HTTP/MCP `generate` endpoint; none was established through this research.
- The public upstream Crew implementation has a distinct pack-producer Box and production source/tests ([`crew_proof_pack.go`](https://github.com/FootprintAI/Containarium/blob/v0.128.0/internal/server/crew_proof_pack.go)), but this **does not mean BoxWeave has Crew orchestration wired**, nor does an independently generated pack constitute an independent black-box Verifier.

**No proof-pack generation, seal, REST verify, test dispatch or privileged mutation was executed during this documentation investigation.** A help/catalog probe proves callability only. Each actual installed future run must inspect the particular executable, configuration and authorization again.

## 4. Proof Pack integration is optional, host-side and safety-gated

The upstream declaration is `.github/containarium.yml` with a bounded `test:` step list; absent declaration may fall back to `make test`, or produce `NO_COMMANDS`. **Never run the implicit fallback without explicitly reviewing it**. Upstream executes declared steps **as root inside the target Box** and limits captured output; it does not automatically redact accidental secrets from command logs. Thus:

1. Coordinator selects a **disposable, immutable, owned nested Box** with appropriate Incus backend; identifies exact host-side `containariumd` and checks actual `proof-pack --help`. Do not use an operator/production host or arbitrary other tenant.
2. Inspect the **specific checked-out commit**, `.github/containarium.yml`, any `Makefile` fallback, script contents, dependency downloads and full trusted working directory. Allow only reviewed bounded, non-destructive commands on disposable fixtures. If not safe, **do not invoke upstream generator**; use a non-root BoxWeave-owned recorder, mark `UPSTREAM_PROOF_PACK_BLOCKED` with reason.
3. If expressly permitted, call the host-side command only through an approved isolated host execution path; record exact original Box UUID/createdAt, source, directory, declaration SHA-256, invoked argv and private output location. A remote `connect(exec)` to a **guest** is not an implicit permission to invoke its **parent host's** root/Incus command.
4. Collect the pack and its exit; `NO_COMMANDS`/`FAILED` do not become PASS; persist its pack digest, step names/status/exits/duration/log digests and bounded sanitized evidence. If a *sealed* pack exists, independently verify it with the appropriate authorized host/REST path and audit anchor when applicable; don't claim a plain generated pack is sealed or independently attested.
5. Add separate BoxWeave case evidence for each black-box action: effective transport, positive/invalid/denied calls, Provider/guest readback, actual effect count, original stdout/exit, cleanup and after-contention success. **Proof Pack is supporting execution provenance, not a feature oracle**.

## 5. Upstream source change → required BoxWeave acceptance selection

| Changed upstream paths/behavior | Mandatory additional BoxWeave probe |
| --- | --- |
| `proto/containarium/v1/**`, `internal/client/**`, `internal/mcp/**`, `internal/server/**` | Compare route/schema/status compatibility with actual installed MCP/REST and BoxWeave adapters, positive/absent/invalid/denied and effect readback |
| `internal/cmd/**`, Cobra shell/client distinction | CLI help/actual invocation vs MCP catalog vs REST support; hidden, renamed or deleted leaf accounting |
| `internal/proofpack/**`, `internal/server/crew_proof_pack*` | Recheck Proof Pack generation, attestations, role separation and safety; do not assume compatible schema |
| `internal/sentinel/**`, `internal/gateway/**`, `internal/auth/**` | SSH trust/retry/outage/auth/expiry; staged actor races and no unauthorized remote dials |
| `pkg/core/incus/**`, `pkg/core/box/**` | Immutable Box identity and lifecycle persistence, guest state/cgroups, stop/start/delete and loss/restart safety |
| `internal/server/*compose*`, `internal/mcp/compose_tools.go` | Reprobe #79 against **native registered route + actual gateway + Box systemd**, keep upstream-owner claim qualified |
| `hacks/install*`, `docs/RELEASE-PROCESS.md`, release workflow | Clean/upgrade/rollback **in isolation**, candidate-only rehearsal, source and published asset digest check |
| `docs/security/CLAIMS.md`, `docs/DOCMAP.md` and design claims | Re-evaluate evidence status and documentation dependencies; **no runtime PASS** from a docs-only change |

**Upstream documentation itself can drift.** Examples seen at v0.128.0: `MCP-PROTOBUF-CONTRACT.md` mentions eight tools despite a broader live MCP surface; `docs/security/CLAIMS.md` describes signing/SBOM as not yet shipped while later release docs/workflows contain signing/SBOM steps; `docs/PROOF-PACK.md` has an older phrase suggesting same-Box pack production alongside newer independent-producer details. Resolve such contradictions against **the pinned source, tagged assets and actual runtime**; preserve both assertions if still uncertain.

## 6. Required report fields and next-Agent handoff

For each upstream-derived case, record `upstream_tag_and_sha`, `installed_daemon_version`, `document_url_pinned`, `contract_source_path`, `runtime_route_or_command`, `adapter`, `proof_pack_mode` (`not_requested / blocked / generated / sealed_and_verified`), `original_case_id`, `oracle`, `outcome`, `confidence`, `permission_gate`, `upstream_issue`, `boxweave_issue` and `next_safe_step`. Documentation is **reference material**, not a PASS. The [report template](REACCEPTANCE_RUN_TEMPLATE.md) is authoritative for complete evidence formatting.

**Conservative default:** on missing direct upstream access, credentials, host authorization, safe command declaration or independent oracle, mark **PARTIAL/BLOCKED**, preserve original request/identity, and continue other cases without escalating permissions.
