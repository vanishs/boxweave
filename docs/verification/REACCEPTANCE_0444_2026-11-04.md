**L FAIL upstream shrink contract:** Direct Containarium 0.128.0 `resize_container` was invoked on exact task-owned Box with disk **25GB→24GB**. The Provider returned *success*, and `get_container` reported disk 24GB; the advertised MCP tool contract states the server rejects shrinks. The Box's harmless file SHA-256 remained `da05d456fc4980fe04d1bf0e0193a0d60f8e76a90b6cd985b87a746a4888e53d`. Guest `df` reported a shared underlying 750G filesystem: physical quota shrink was NOT established. After this test, a combined resize requested CPU 2→1, memory 3GB→2GB, disk **24GB→25GB** and succeeded; readback and guest CPU/memory matched, original file hash unchanged.

**S+T source fix in v0.44.4 candidate:** `resource_size.py` uses strict positive decimal/binary disk-size comparisons and fails closed for unsupported or unavailable values. Agent `mcp_gate.py` now performs a current authenticated `get_container` read before forwarding disk resize; rejects shrink or unverified size. App `provider_rest.py` does the same before its REST PUT, and Web `lifecycle.py` refuses such requests already at the plan stage. Target-only read, no credential export, no implicit retry/host modification. New tests cover shrink/unknown/no-provider-write, equal size/grow, CPU and memory unaffected; source release/installer helper manifests and code inventory include the new standalone module. **Remaining U:** the preflight cannot guarantee atomicity against two concurrent clients or actual physical disk limits; upstream needs a server-side guard.
