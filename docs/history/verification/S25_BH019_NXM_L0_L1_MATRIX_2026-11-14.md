### Interpretation: what this DOES and DOES NOT establish

**Strongly supported:** deeper UserNS creation is possible for root in both layers; it does **not** automatically allocate a new AA policy namespace. L1-created Box still inherits the older policy namespace despite an enforced process profile. Nonroot UserNS create permission materially differs across these two layer contexts, for three independent identities, without a simple UID/GID identity mismatch. Root-local `CAP_MAC_ADMIN` alone is insufficient proof of AA policy admin.

**NOT PROVEN:** actual numeric `user_ns->level == view_ns->level`, kernel rejection site/LSM for nonroot EACCES, independent AA policy load/replace/remove, per-depth policy ownership, cross-tenant denial, enforcement of ancestor policy, or safe recursive L2→L3 Incus. In particular, L0-visible `unconfined` is relative to its view, **not proof** that outer enforcement exists or is absent. No AA profile was loaded or replaced in this matrix, because the current L1 policy view may be ancestor-visible.

**Upstream code cross-check:** the upstream Linux `aa_policy_view_capable` checks visible namespace, suitable root in userns and (outside init userns) a userns-level-to-view-ns-level match plus the unprivileged AA policy feature; `aa_policy_admin_capable` additionally requires a valid `CAP_MAC_ADMIN` path and unlocked policy. This is a **source-based causal hypothesis** compatible with the actual inherited policy view, not a direct numerical level measurement in these tests. Source: [Linux `security/apparmor/policy.c`](https://linux.googlesource.com/linux/kernel/git/torvalds/linux/+/54ac9ff8f1196afc49d644a1625e0af1c9fcf7f5/security/apparmor/policy.c).

## Next ordered experiments with high information density

1. **E5 root-cause isolation, but only in another fresh disposable Box:** each individual securityfs path/operation should be a separate **bounded subprocess** with per-step immediate printed marker and short timeout; first perform only stat/list metadata, then narrowly selected harmless reads. Stop on first blocked or ambiguous resource. This is necessary because the previous all-or-nothing E5 script printed nothing before its timeout; blaming a specific AppArmor path would be fabrication.
2. **Policy-view permission reasoning (no writes):** independently audit exact kernel/Incus code paths for `labels_view`, AA namespace depth alignment, and `policy_ns_capable`. Correlate with L0 own namespace / L1 inherited namespace, CAP_MAC_ADMIN in userns, and prior parser rc243. Do not guess numeric levels from nsfs `EPERM`.
3. **Nonroot `EACCES` distinction:** repeat 3 UID controls with host-approved read-only security audit evidence, compare AA versus seccomp and mapped parent identity. Use one additional narrow A/B on a new disposable Box only after relevant boundaries are understood; do not relax/disable AppArmor for a green outcome.
4. **Eventually, safe per-depth delegation verification:** only after there is a verified **own child policy namespace** with a separately enforced parent and strict sibling/ancestor negative controls should a unique harmless test profile ever be loaded. Do not write into the currently inherited L1 policy namespace or claim secure arbitrary-depth recursion from UserNS alone.
