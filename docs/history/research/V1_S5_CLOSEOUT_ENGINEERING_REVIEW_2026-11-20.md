# BoxWeave v1 — S5 closeout engineering review: recovery boundaries, implementation gaps and evidence

Date: 2026-11-20 PT. Audited protected v1: [36e7933e12f8](https://github.com/vanishs/boxweave/tree/36e7933e12f83d129a382efc917f8f6c2b3b6820).

**Purpose:** a source-backed technical reference for closing S5, not a second phase card, a new architecture mandate, a completed design for approval, or a test receipt. The [S5 card](../development/phases/05_RELEASE_ACCEPTANCE.md) remains the execution entry. Read individual sections when a relevant implementation or acceptance decision arises. All internal source links below are pinned to the audited baseline, not mutable branch tips.

## 1. Owner decisions and engineering consequences

The owner clarified three boundaries on 2026-11-20:

1. S5 is the final v1 feature-development phase. After the recovery/diagnostic work, freeze v1's product surface; fix defects, complete verification and publish only a supported contract. Do not turn every observed inconvenience into a feature.
2. Strong deep recursive security is not a prerequisite for the v1 stable release. Retain the independent owned-controller model and supported ordinary flat isolation; do not promise per-depth hostile tenant AppArmor/BPF/ID-map/quota separation that has not been established. Actual supported nesting is conditional and must be verified. #150 strong isolation research may remain open after v1.
3. The desired product experience is that, provided BoxWeave itself remains operational, an authorized Agent can diagnose and repair owned Box problems through MCP with the user's authorization when required. The specific anti-self-approval mechanism is to be discussed during implementation. This is a product goal, not authorization for Agent self-approval, for arbitrary host maintenance, or for unsafe release of an unproven resource lock.

Interpretation: distinguish release scope from a failure of a supported capability. Removing strong recursive assurance from the v1 feature claim is a real scope decision, not retroactive PASS for failed cases. It does not relax flat peer/forward isolation, authorization, provenance, quotas actually advertised, or the independent release gates. No decision here waives real public IPv6, physical-host crash evidence or any other unrelated mandatory condition. If owner-approved recovery cannot safely repair a condition, report it and retain its barrier; never make the product goal a justification to invent success. A broken controller, unreachable native service, unavailable trusted approval channel, or unresolvable evidence is an explicit blocked condition, not license to route around protection.

## 3. Why recovery is a legitimate final product capability

The product is an owned multi-Box environment, not a host administration console. An Agent can already create and update Boxes, run development work, recover receipts, configure owned peer/forward relationships and remove owned dependencies. However a single ambiguous original can fence a Box, port, name, or in some cases the whole Project. The normal authenticated interface can find it but cannot repair it. That makes the development loop incomplete even though the basic primitives work.

The smallest coherent addition is a domain recovery facade shared by the current Host CLI and the proposed single operation_recover MCP tool; use existing read surfaces for discovery. No extra task engine, generic host shell, generic ACL editor, root command forwarding, arbitrary recovery script, cross-Layer privileges, or separate service merely for orchestration. The existing CLI remains the emergency path when the controller or its dependencies cannot serve the supported workflow.

## 4. The critical distinction: original outcome versus protection

Existing [Operations contract](https://github.com/vanishs/boxweave/blob/06d27434b11997e9254822c122483c9dacba12a3/docs/design/OPERATIONS.md) permits UNKNOWN to settle as SUCCEEDED or FAILED with sufficient independent evidence. Existing Delete and Peer recovery do exactly that. The S5 wording that the original UNKNOWN must be retained is therefore best read as retaining the original operation identity, intent, native ID and historical UNKNOWN event, not forbidding an evidence-backed current-state correction.

| Original result | Protection / reconciliation | Required behavior |
| --- | --- | --- |
| Native effect genuinely unproved | blocking | UNKNOWN, retained claims; no replay |
| Native effect independently established successful | reconciled | same original may become SUCCEEDED by domain-specific transaction; preserve UNKNOWN event and recovery link |
| Definitive failure with adequate no-effect/partial-effect handling | reconciled or still blocked depending on resource invariants | FAILED only if supported proof permits it; never treat native failure as no effect by default |
| Still unproved, approved release permissible for this exact claim | released after review | original remains UNKNOWN; separately record authorization and release, never imply completion |
| Incomplete Project-wide network change or unresolved dependent claims | blocked | generic release forbidden even with user confirmation |

A fully authenticated user may authorize risk, but cannot turn a missing native fact into evidence. A recovery action has its own admitted identity/idempotency key and original-operation link. Repeating it returns the same recovery receipt and never repeats the earlier native request. A compensating change, if separately designed and approved for that action, is a **new** operation with its own intent, native receipt and safety checks, not another execution of the UNKNOWN original.

A manual HOLD and UNKNOWN describe different things. A future owner-requested voluntary hold could be an explicit protection reason independent of native outcome; do not fabricate UNKNOWN merely to pause a healthy Box. No new HOLD API or state is authorized by this review. If the owner decides it is essential to recovery, first define target scope, authorized release and admission conflict rules. Prefer a durable proof/claim disposition over a second competing Box status machine.

### Recovery correctness pressure points

- In Schema5 most claim exclusion is derived from original operation state and recovery_audit RELEASED, not physical deletion of claim rows. Peer has a special Project-wide barrier and cannot be bypassed by general release. Forward claims, address fences, GC, Delete parent/children and readiness have additional domain conditions. Releasing one ordinary claim cannot be assumed to release all of them.
- Admit currently refuses ordinary work while the existing Peer or cascade Delete Project barrier is active. A recovery route that simply uses Admit as an ordinary mutation may deadlock on the very original it needs to resolve. A special recovery admission must be bound to the same original and its claims; no broad exemption, arbitrary resource key, or second native dispatch. Serialize competing recovery actions and CLI interaction in the shared ledger, with fresh principal/identity/intent/version checks.
- Challenge issuance is a state write. A mixed-mode tool that can write must advertise conservative mutation/destructive annotations; retain ordinary read-only operation_get, box_get and Activity for diagnosis. Never mark the whole mixed tool readOnlyHint=true merely because one mode reads.
- Existing native observation uses bounded GET; do not reintroduce context-cancel-driven native cancellation through WaitContext. Incus terminal records are short-lived (recorded earlier 4-second present / 6-second missing evidence). Missing receipt, a familiar name, matching current value, or inactive ID alone is not a generic outcome oracle.
- Commit outcome uncertainty applies to recovery as well. Prove the new recovery decision, original receipt, dependency states and consumed approval form a consistent durable outcome; after lost response or service restart read the original recovery receipt, not resubmit the native work. Audit success from the actual transaction, not from a log message emitted before commit.

## 5. Recovery coverage matrix: classify by evidence, not by tool name

This is a development reference, not a claim of implemented support. The first group should be implemented before difficult uncertain-effect cases. Use existing domain-native postconditions if demonstrably sufficient; otherwise explicitly return BLOCKED, never weaken the oracle.

| Original class | Existing useful oracle | Necessary closeout behavior |
| --- | --- | --- |
| Create, UUID already known | Exact original marker, native UUID, full requested shape, readiness and original receipt where required | Settle only when all promised postconditions are proved. If bound but partially created, preserve evidence and design allowed next cleanup separately |
| Create, UUID missing | ObserveCreatedByOperation + repeat exact UUID observation | Bind original identity with trusted review; no adoption, no fabricated ACK, claim not automatically released |
| Start / Stop / Update | Owned UUID/incarnation, original native receipt, exact requested native postconditions | Current Running or matching config alone is not proof of causal completion; classify missing/foreign/replaced/active separately |
| Exec | Terminal original native ID, exact recorded output paths and guest exit metadata | Preserve completed nonzero exit as completion, not transport failure. No output or 126/127 alone does not prove no execution; never re-execute original command to recover it |
| File exclusive create | Exact path/UUID, intended bytes digest and original SFTP evidence | Existing file with matching bytes may be a concurrent writer's file; lack of a native operation ID is normal. Do not infer causality or add unsafe conditional replace/delete |
| Forward create/delete | Exact owned device spec, original native operation where required, current device/listener identity, pending claim | Add action-specific UNKNOWN settlement only if exact native+ledger proof sufficient. Preserve reserved endpoint/no new create when ambiguous; never use arbitrary device removal |
| Peer grant/revoke | Existing completed Root journal, exact plan digest, independent ACL/kernel proof, pending direction | Use current PRS reconciliation. Partial or incomplete journal requires separately designed contained repair/compensation and verification; no generic unlock/remutation |
| Dependent Delete | Original parent, linked children, all relevant peer/forward/fence state, exact Delete receipt and absence | Reconcile children and dependency barriers first; atomic tombstone and release only if original causal proof exists. Missing receipt stays UNKNOWN |
| Readiness | Original fixed probe and terminal exit, exact incarnation and observation validity | Before dispatch can settle no-effect; after ACK lost without evidence remains UNKNOWN, current ready observation is a different operation |
| Exec GC | Exact original stream, retention window, GC audit, native existence | Release only applicable stream protection after review, keep old outcome honest; do not delete again or fabricate expiration |
| Operation cancel | Original cancellation record and target terminal evidence | Cancel request is not native cancellation or rollback; detached Exec unsupported remains explicit |

Every supported MCP mutation should appear in at least one row or have a documented exclusion. A system-wide diagnostic should identify the actual blocking original/claim and safe recovery mode, not merely say RESOURCE_LOCKED. If a partial-effect recovery cannot be made safe within S5, document exact limits and discuss a narrower contract before claiming recovery PASS. Operator maintenance remains local: service/bootstrap/dependency updates, foreign resources, root policy changes, global credentials and host failures are not owned Box repair methods.

## 6. User approval: unresolved mechanism, fixed trust requirements

The owner explicitly defers choosing the anti-self-approval mechanism to implementation discussion. Do not choose or implement it based on this review. Separate four facts:

- An authorized management Actor can perform regular owned Box work under current product semantics.
- A model-generated statement of consent is not proof that a human approved an exact recovery.
- A UI confirmation may be valuable UX, but the remote server must know whether it was given a trustworthy, action-bound assertion; a caller-supplied boolean, arbitrary reviewer name, or challenge returned to the same caller cannot prove independent approval.
- A valid authorization cannot invalidate an immutable native safety invariant. Partial Peer/GC/Delete/network ambiguity still requires action-specific checks.

The present Host CLI is secure by a **different** trusted entry: recoverLocal checks root; recoverWorker verifies actual root Unix peer and restricted service identity. The challenge hash binds reviewer, original identity, observation, timestamp and state. Challenge alone is not a second factor when the same Agent can request it and return it. It cannot simply be made public and described as human approval.

Relevant external evidence checked 2026-11-20:
- [OpenAI MCP server guidance](https://developers.openai.com/plugins/build/mcp-server#tool-annotations-and-elicitation) distinguishes tool annotations and server authorization; annotations support confirmation behavior, not backing server authorization.
- [ChatGPT custom MCP testing guide](https://developers.openai.com/api/docs/guides/custom-mcp-server) describes default write confirmation and remembered choices within a conversation. This is not documentation of a unique server-verifiable per-action human signature.
- Exact [Go MCP SDK v1.8.0 server docs, Multi Round-Trip Requests](https://github.com/modelcontextprotocol/go-sdk/blob/v1.8.0/docs/server.md#multi-round-trip-requests) describe the newer 2026-07-28 input-required pattern and legacy fallback. The handler may execute twice during elicitation; it must not dispatch a mutation before an independently accepted approval. RC8 uses Stateless=true, JSONResponse=true and no propagated request cancellation. Prove actual negotiated protocol/capability and actual ChatGPT behavior before assuming any elicitation feature is available.
- [MCP URL elicitation rationale](https://blog.modelcontextprotocol.io/posts/2025-11-25-first-mcp-anniversary/) describes out-of-band browser interaction. Acceptance of a navigation prompt is not proof that a later human approval was completed. Modern protocol availability does not establish support on this exact connector.
- RC8 has an existing browser OAuth consent boundary ([control/oauth.go](https://github.com/vanishs/boxweave/blob/36e7933e12f83d129a382efc917f8f6c2b3b6820/internal/control/oauth.go#L152-L227)) with exact origin, bounded form, password verification and no-store headers. OAuth enrollment grants management authority, not specific recovery consent. It is useful precedent for an independently secured interaction, not a ready-made recovery authorization.

Candidate classes to compare during implementation (not approved architecture):

| Candidate | Trust question / evaluation |
| --- | --- |
| Platform-supplied action-bound approval assertion | Does the exact client provide one that BoxWeave can independently authenticate, validate for this original/action, and consume exactly once? Verify actual request and negatives; no assumption from UI alone |
| Independent trusted user interaction such as URL-mode elicitation / narrowly scoped browser consent | Can the user independently authenticate and review the exact safe intent without exposing the approval credential to the Agent? Requires separate owner decision on endpoint/UI, threat model and host configuration |
| Host local review | Existing trusted fallback, but not desired normal UX. Keep supported as emergency path and report missing remote capability honestly |

For any accepted solution require exact Layer, original and recovery identifiers, native UUID/incarnation or original Create identity, intended scope and digest, relevant poststate fingerprint, authenticated approver, expiry and single-use semantics. Revalidate live requesting Actor and state immediately before settlement. A changed snapshot/ownership/intent requires new review. No approval obtained via ordinary Agent-controlled data alone. Rate-limit and audit pending, denied, expired, consumed and stale approvals. Never disclose authentication material in MCP payload, Activity, logs or guest files. No reusable approval bearer given to model as trusted proof by itself. Test direct malicious/self-approved calls, copied/replayed/expired requests, wrong original, cross-Layer, stale poststate, revoked requester, concurrent confirm, service restart and lost confirm response. Test explicit deny as well as approve. If no trustworthy mechanism is available, high-risk recovery remains blocked until a reviewed solution or explicit owner scope revision; safe read-only and provable reconciliation development need not wait.

## 8. Data model, transaction and compatibility

Schema5 already stores operations (Layer, Actor, Token, request/key/intent digest, work_ref, agent_ref, box_uuid, incarnation, native ID), events, resource claims, recovery_audit, network bindings/fences, peer_grants, forward_claims, Exec/GC and OAuth data. This is adequate for most discovery. Do not start S5 by redesigning the whole DB or adding a task table. First determine what cannot be represented safely.

Likely gap: the current recovery_audit has original operation ID, time, reviewer, decision and evidence digest, but no explicit durable recovery request/approval linkage, structured disposition, or consumable approval record tying issuer, original and recovery together. Determine whether a typed linked recovery original + new narrowly scoped rows or a compatible extension meets the exact transaction requirements. Never overload string labels with authorization meaning. No raw approval secret, raw guest bytes, or unredacted Native error in DB diagnostics. Establish uniqueness and transaction invariants, not a schema-number goal. If the selected approval/recovery model requires DDL, perform an explicit compatibility decision and preserve all existing original UNKNOWN records. Do not blindly keep Schema5 while changing its expected table layout: validateExistingSchema rejects undeclared schema changes, and final supported v1 freezes a data compatibility baseline. Document fresh-lab schema policy versus retained/live RC8 transition separately. No unapproved live reset, resource adoption or deletion.

Ordinary worker, CLI and recovery paths must share one concurrency model. Use existing exact claims and guard re-read in the intended SQLite write transaction; domain native evidence is observed outside SQLite, so repeat exact observations at the correct point of use and use domain fences against independent changes. If the underlying native state can still change or evidence is incomplete, preserve UNKNOWN rather than pretending a DB transaction makes an external operation atomic. Fault injection should demonstrate the guard rejects the unsafe variant.

## 9. Highest-value investigation: #151 and Exec provenance

[Issue #151](https://github.com/vanishs/boxweave/issues/151) is OPEN, explicitly S5 release-blocking. It concerns a **fresh** readback operation after installed service restart, not necessarily the previously completed exit-126 or exit-127 original. Original a529cc5a3bb2f64714455d0612161a80 from [43776449453](https://github.com/vanishs/boxweave/actions/runs/43776449453) was not independently classified. Earlier green reruns must not erase the incident.

Read the failed job(s) and preserve what original evidence actually remains. Map failure at client initialization/reconnect, transport response, admission, ACK, native terminal metadata, SQLite finalization, output read, poll deadline or test assertion; do not choose a root cause by intuition. A disposable exact candidate can repeat **new distinct benign readback cases**, not replay an uncertain original. Use native terminal observer before receipt expiry; correlate original request/key, Tracking/native IDs, no additional native effect and actual output/exit. Deliberately vary controller restart, native response and read deadline using approved independent harnesses. A positive rerun without an original classification is incomplete; if old receipt no longer exists report evidence lost and identify whether a supported safe refusal or corrected reproduction establishes the current contract.

Existing [native/box.go](https://github.com/vanishs/boxweave/blob/36e7933e12f83d129a382efc917f8f6c2b3b6820/internal/native/box.go#L392-L480) uses read-only GET polling and exact original inactivity checks. Do not add a broad retry because a client readback failed. Existing [Exec quota classifier](https://github.com/vanishs/boxweave/blob/36e7933e12f83d129a382efc917f8f6c2b3b6820/internal/native/exec_quota.go) is intentionally narrow: volume-state preflight can refuse known low space, but unknown usage proceeds conservatively; only exact original pre-start spool failure without return/output metadata is proven no Guest execution. Earlier BH-018 showed identical 127 failure can occur after guest side effects. Distinguish missing output, truncated output, command failure and uncertain dispatch.

Archive is bounded: live exact Box native reads up to 16 MiB, after deletion private archive 1 MiB prefix per stream, total 256 MiB, 4096 files, 7-day retention. Archive capture is best effort; redacted availability reason and exit evidence must survive deletion even when bytes cannot. ## 10. Strong nested assurance: keep the useful feature, narrow the claim

There are three distinct contracts:

- Strong recursive multi-tenant isolation over arbitrary depth: independent AppArmor policy namespaces/admin, BPF device delegation and crash-safe sibling UID/GID allocation, per-depth hostile isolation/quotas. Not a v1 stable-release requirement by the latest owner decision; no unsupported guarantee or unsafe fallback. #150 remains a future research issue rather than a mandatory implementation blocker for narrowed v1.
