## Authorized 0.10+ remediation

- The 2026-10-29 owner request authorizes **small, independent commits directly to main**, without a PR, for the remediation R-00–R-09; do not force-push. Confirm the current main SHA before each commit and reject unexpected changes. Never use an unreviewed working tree or wipe unrelated work. Remote repository-only edits via the approved GitHub connection are permitted; lack of a checked-out/test-capable environment must be recorded rather than invented.
- Restore useful `install.sh` host bootstrap and `boxweave.sh` management experiences via a reviewed new design. Support the owner-approved cross-platform App catalog and native/WSL transports; never silently migrate existing client settings. Fresh installation/update/repair come first; **no automatic 0.5.1 data migration**.
- Start the version line at `0.10.0`. Treat `A.B.C` as: increment B for a completed new feature slice and reset C to zero; increment C for fixes of existing behavior. Align `VERSION`, `pyproject.toml`, `web/package.json`, and the root metadata in `web/package-lock.json` on each version change. Do not bump for an empty promise. Use a distinct, descriptive English commit for each coherent slice.

## Trust and execution

- Historical source revisions, including `archive/0.5.1`, are read-only behavioral evidence, not a merge source. Their installers, bootstrap assumptions and test claims must not be transplanted unexamined.
- Never modify real host, Incus, Provider, SSH/firewall, token/key trust, private credentials, external network routes or public TLS without separate **specific environment authorization**. Repo source code for these operations can be drafted, but not run against a real host under the repository-write authorization. Prefer safe preflight, explicit operator confirmation, idempotent owned state, isolated boundaries and rollback/repair instructions.
- Do not read or export private keys, signing secrets, JWT values or production DBs. Preserve original evidence, ignored directories, historical SHAs, installed services, and legacy branch. No implicit provider upgrade, SSH trust-on-first-use, tenant/policy mutation or live inference.
- Only conduct Linux installation/real browser/Provider tests in a specifically approved prepared non-root Linux environment. The standard validation lane is `python scripts/check_knowledge.py`; in the prepared LXC, `.venv/bin/python scripts/validate.py` and optionally `--browser`. These are not host/provider acceptance. Check executable help and syntax before integration tests.
- Maintain `REQ/AC -> ADR/TASK -> code/tests/evidence` traceability. Follow [MAINTENANCE](docs/process/MAINTENANCE.md). Update the authoritative scope/requirements if an approved outcome changes, and keep [historical comparison](docs/verification/ARCHIVE_051_TO_MAIN_AUDIT.md), [risks](docs/verification/OPEN_RISKS.md), source register and handoff aligned. Preserve old reports as historical evidence.
- For every slice record *what changed*, *what was actually tested* (command, environment, exit code and evidence), *what remains untested*, *blockers*, and next Agent's executable checks in [remediation verification queue](docs/verification/REMEDIATION_TEST_QUEUE.md). A static code review is **S**, historical documentation **D**, genuinely run tests **T**, and untested properties **U**. Never report source code, fixture or CI as a successful real-host install.

## Fast BoxWeave development and Agent-driven validation

Use [Agent development/test workflow](docs/process/AGENT_TEST_WORKFLOW.md) for both reused and genuinely clean test Boxes. These are **developer working rules**, not a new BoxWeave testing product or authorization for any real host.

- **Fastest honest evidence first:** map each change to a specific success condition. Run affected source/unit/fixture tests before a separately approved live nested test; do not rerun a complete installer, every suite or create a new Box after each small edit.
- **Pin exact identities:** record source commit/reviewed diff, installed release and *running* app/worker version, outer Provider/project and exact test Box identity, and whether the Box is reused or genuinely clean. A preinstalled or future cloned Box does **not** prove a fresh install.
- **Keep layers separate:** the usual test Box contains inner BoxWeave + Containarium + Incus, with an optional *different* nested workload. The outer BoxWeave remains the independent controller; do not rely on a broken inner stack to preserve or recover the failure scene.
- **Support both execution modes:** (a) Agent self-selects/adapts steps **within an existing specifically authorized scope**, or (b) Agent proposes a plan and obtains approval before environment writes. Missing/ambiguous grants mean repo-only safe checks or plan drafting. Either mode requires renewed specific approval for new target, privileged/destructive action or expanded scope.
- **Distinguish proof levels:** passing fixture/CI is not real Provider acceptance. A claimed live nesting/MCP success requires authenticated observation, verified target identity, actual Python `hello world` stdout **and exit 0**, with resource cleanup/retention recorded independently.
- **Preserve failures:** timeout/lost Provider response means **UNKNOWN**, not proven failure. Observe the *original* operation and Box; never automatically retry an uncertain write, reset a reused Box, repair SSH trust or destroy a fault scene.
- **Handoff in one short record:** changed revision, exact check/target/exit, PASS/FAIL/PARTIAL/UNKNOWN by proved scope, source/fixture/live evidence class, retained resources, and smallest next action. Append actual checks and untested claims to [verification queue](docs/verification/REMEDIATION_TEST_QUEUE.md).

Proposed [D0-D2 diagnostics](docs/design/DIAGNOSTICS_PROPOSAL.md) and [E0-E4 snapshots/clones/fingerprints](docs/design/BOX_ENVIRONMENT_PROPOSAL.md) are **NOT IMPLEMENTED** and must not be treated as available test tooling.

## User-facing documentation conventions

- Describe the current product as **BoxWeave**, using its `0.X.X` release version. Keep obsolete archived-release and numbered development-stage narratives out of current user-facing prose, especially README; retain historical evidence in the historical records.
- This is a narrative/branding convention, not a ban on the words `archive`, `phase` or `v2`. Keep accurate ZIP/archive terminology, compatible CLI options, upstream protocol/API versions, technical phase fields, existing paths/service identifiers and useful developer-history links. Never rename runtime identities or remove compatibility to satisfy a word blacklist.
- Use tables for supported OS/Agent/SSH combinations, installer flags, and management commands.
- **Always list client Apps alphabetically (case-insensitive)** in code constants, interactive selectors, Web UI, support matrices and docs. Do not append new Apps out of order. The ordered catalog is: Antigravity, Claude, Codex, Copilot, Cursor, OpenCode, Qoder, TRAE, ZCode.
- **Unify installed client generator output:** every `boxweave client` profile must emit self-contained Python 3.11+ source on stdout, with `#!/usr/bin/env python3` as the literal first line, followed by comment-only banners and guidance. Never reintroduce per-App PowerShell output or place separators above the shebang. Write successful wizard prompts/status as `#`-prefixed lines to stderr, keeping stdout code-only; confirm by compiling the exact generated script and testing `--output`. Existing standalone legacy client utilities are not the installed generator.
- All persistent **MCP-over-SSH registrations** (Windows native/WSL, Linux/macOS, and legacy client paths) must include `-o ServerAliveInterval=15 -o ServerAliveCountMax=4` in the actual registered SSH argv, not only in installation or diagnostic probes. Test both and preserve strict SSH host-key checking. Keepalive does not reconnect a terminated MCP session.
- Do not claim the streamed default installer works until reviewed release artifacts and a complete host/launcher bootstrap have been accepted with real tests.
